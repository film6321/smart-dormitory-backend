# บทที่ 5 สรุปผลและข้อเสนอแนะ

ฉบับอ้างอิงระบบและหลักฐาน ณ 14 ตุลาคม 2569

## 5.1 สรุปผลตามวัตถุประสงค์

| วัตถุประสงค์ | ผลที่พัฒนา/ตรวจได้ | ขอบเขตหลักฐาน |
|---|---|---|
| วงจรผู้พักตั้งแต่สมัครถึงย้ายออก | สมัคร 4 ขั้น สัญญา ย้ายออก ลบและสมัครใหม่ | IT/RT/UA |
| เชื่อมงานห้อง บิล ซ่อมและ Visitor | ข้อมูลและสถานะใช้ PostgreSQL พร้อม role/ownership | SR/UT/IT และ runtime บาง flow |
| เชื่อม OCR/Face/payment | wrapper และ error/fallback ไม่สร้าง engine ใหม่ | UT/mock; provider จริง OS |
| UX/UI ไปแนวเดียวกัน | shared components, Skeleton/action spinner, ตารางและค้นหา | frontend tests และ UA รวม |
| ตรวจและจัดเอกสาร | 5 บทและรายละเอียดบท 4 แยก 11 โมดูล | อ้างรายงาน QA/โค้ดปัจจุบัน |

Runtime ยืนยันการย้ายออก/purge ผู้พักทดสอบ คืนห้อง ลบข้อมูลที่ตรวจครบ 16 ประเภท ลบไฟล์ 10/10 และคิว COMPLETE 11/11 โดย User ยังอยู่ ผู้ใช้ยืนยันสมัครใหม่ได้และใช้งานปกติ ไม่ใช้การยืนยันรวมแทนผลทุก edge case

เพิ่มการยินยอมข้อมูลสมัครและข้อมูลชีวภาพแยกวัตถุประสงค์ก่อนเริ่มเก็บข้อมูล บันทึกเวลาและรุ่นข้อความในฐานข้อมูล พร้อมตรวจสิทธิ์ผ่าน API ผล regression ล่าสุด 185/185 และ 119/119; ยังไม่ใช้แทนการตรวจหน้าจอจริงหรือการรับรอง PDPA ครบทุกด้าน

## 5.2 ปัญหาและบทเรียน

การกรอกใบสมัครครบไม่แปลว่า Admin ตั้งค่าสัญญาครบ การสร้าง QR ไม่แปลว่ามีเงินเข้า และการอนุมัติซ่อมไม่แปลว่าปิดงานแล้ว ต้องแยกเงื่อนไขและชื่อสถานะใน UI/API ให้สอดคล้อง

การลบแถว Tenant ไม่เพียงพอ ต้องตรวจบิล งานซ่อม draft เอกสาร รูปและ cleanup ภายนอก พร้อมรักษา User เมื่อต้องสมัครใหม่ QR เก่าที่ไม่เคยส่งหลักฐานต้องไม่ถูกนับเป็นการโอนค้าง แต่ข้อยกเว้นต้องไม่เปิดให้ลบธุรกรรมที่ยังตรวจเงินจริง

เอกสารและ Docker image อาจตาม source ไม่ทัน การส่งมอบต้องระบุรุ่น/วัน หลักฐาน migration/build/runtime และแก้เอกสารที่เคยบอกสมัคร 3 ขั้นหรือ ARCHIVED ไม่ใช้ประวัติเก่าเป็นกฎปัจจุบัน

## 5.3 ข้อจำกัด

- หน้าความยินยอมใหม่ยังรอ browser acceptance; การถอนผ่านผู้ดูแล ยังไม่มีปุ่มถอนอัตโนมัติ
- ไม่มีผลรับรองกล้อง ประตู/Edge SMS หรือ provider จริงครบระบบ
- ไม่มี accuracy, แบบประเมินความพึงพอใจ หรือ sustained production benchmark
- Read state แจ้งเตือนยังเป็น browser-local และ fallback refresh 30 วินาที
- วันหมดสัญญาเองไม่ใช่การ purge ใบหน้า ต้องใช้ flow ย้ายออก/ลบ
- Annual retention ต้องเปิดโหมดและทบทวน guard ก่อนใช้งานจริง
- นโยบาย purge ลบข้อมูลการเงินที่ผูกผู้พัก จึงไม่ใช่ระบบบัญชีถาวรหรือคืนเงินธนาคารอัตโนมัติ

## 5.4 ข้อเสนอแนะ

1. เติมภาพหน้าจอข้อมูลทดสอบและบันทึกวันที่ให้ตรงบท 4 พร้อมปิดข้อมูลส่วนตัว
2. จัดรูปเล่ม ชื่อผู้จัดทำ/สถานศึกษา และบรรณานุกรมจากแหล่งที่อ่านจริงตามเกณฑ์หลักสูตร
3. ทดลอง backup/restore ทั้ง DB และ files พร้อมหลักฐานก่อนส่งมอบ production
4. ทบทวน dependency, secret, TLS และ public ports ตาม deployment จริง
5. หากขยายขอบเขต ให้วัด provider/อุปกรณ์จริงและ long-running performance แยกโครงการทดสอบ
6. หากต้องการประเมินผลกับผู้ใช้จำนวนมาก ให้ออกแบบแบบประเมินและเก็บข้อมูลจริงก่อนสรุปเชิงสถิติ

ไม่มีการแนะนำให้เพิ่มโมดูลหรือแพ็กเกจเพียงเพื่อให้เล่มดูใหญ่ขึ้น งานต่อยอดต้องอิงความต้องการและข้อจำกัดที่ตรวจพบ
