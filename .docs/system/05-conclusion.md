# บทที่ 5 สรุปผล อภิปรายผล และข้อเสนอแนะ

บทนี้สรุปผลการพัฒนาระบบต้นแบบบริหารจัดการหอพักผ่านเว็บแอปพลิเคชันตามวัตถุประสงค์ของโครงงาน อภิปรายผลจากการพัฒนาและการทดสอบ ปัญหาและข้อจำกัดที่พบ ตลอดจนเสนอแนวทางสำหรับการทดสอบและพัฒนาต่อไป เนื้อหาอ้างอิงหลักฐานที่รวบรวมถึงวันที่ 19 ตุลาคม พ.ศ. 2569 โดยแยกผลทดสอบอัตโนมัติ การเชื่อมต่อฐานข้อมูล การตรวจระบบขณะทำงาน และผลที่ผู้ใช้รายงานออกจากกัน

## 5.1 สรุปผลการดำเนินงาน

โครงงานได้พัฒนาระบบต้นแบบสำหรับจัดการข้อมูลและกระบวนการสำคัญของหอพักผ่านเว็บแอปพลิเคชัน โดยมีส่วนติดต่อสำหรับผู้ดูแล ผู้พัก และผู้มาติดต่อ ระบบประกอบด้วยการจัดการบัญชีและสิทธิ์ การสมัครและจัดการผู้พัก ห้องพักและสัญญา บิลและหลักฐานชำระเงิน งานแจ้งซ่อม ผู้มาติดต่อ การแจ้งเตือน รายงาน และการเชื่อมต่อ OCR กับ Face Verification ผ่าน API ภายนอก สรุปผลเทียบกับวัตถุประสงค์ได้ดังตารางที่ 5.1

**ตารางที่ 5.1 ผลการดำเนินงานเทียบกับวัตถุประสงค์ของโครงงาน**

| วัตถุประสงค์ | ผลการดำเนินงาน | ขอบเขตผลที่ยืนยัน |
|---|---|---|
| 1. พัฒนาระบบต้นแบบผ่านเว็บแอปพลิเคชันสำหรับจัดการข้อมูลหอพักและกระบวนการของผู้พัก | พัฒนาระบบเว็บโดยใช้ React และ TypeScript สำหรับส่วนติดต่อ และ Node.js, Express.js และ TypeScript สำหรับบริการเว็บ ใช้ PostgreSQL เป็นฐานข้อมูลหลัก และ Redis สำหรับข้อมูลชั่วคราวและกลไกควบคุมบางประเภท | ตรวจสอบจากซอร์สโค้ด การทดสอบที่ระบุในบทที่ 4 และ runtime บางกระบวนการ ไม่ใช่การรับรองระบบ production ระยะยาว |
| 2. เชื่อมโยงการจัดการห้อง ผู้พัก สัญญา บิล งานแจ้งซ่อม และผู้มาติดต่อ พร้อมควบคุมสิทธิ์และสถานะ | พัฒนากระบวนการสมัคร 4 ขั้น การจัดการห้องและความจุ สัญญา การชำระและเครดิต การแจ้งซ่อมตามลำดับสถานะ การจัดการผู้มาติดต่อ และการย้ายออก/ลบข้อมูลผู้พักตามเงื่อนไข | มีผล Integration บนฐานข้อมูลแยก เช่น ห้องและความจุ 8/8 กรณี การเปลี่ยนห้องและเครดิต 12/12 กรณี และงานแจ้งซ่อม 38/38 กรณี; ผลแต่ละชุดจำกัดตามกรณีที่ทดสอบ |
| 3. รองรับการเชื่อมต่อ OCR และ Face Verification ผ่าน API | จัดทำส่วนเชื่อมต่อบริการภายนอก การตรวจข้อมูลและสิทธิ์ การจัดการผลผิดพลาด และ flow ขอความยินยอมก่อนส่งภาพ โดยไม่ได้สร้างโมเดล OCR หรือ Face Recognition ขึ้นใหม่ | OCR ยังไม่มีชุดภาพพร้อมคำตอบอ้างอิงสำหรับคำนวณความแม่นยำ ส่วนผล Face ที่รายงานมีเพียง 4 ภาพและใช้สรุปแทนความแม่นยำโดยรวมไม่ได้; ยังไม่ยืนยัน provider จริงครบวงจร |
| 4. จัดทำหน้าจอและกระบวนการใช้งานสำหรับผู้ดูแล ผู้พัก และผู้มาติดต่อ | พัฒนาหน้าจอตามบทบาทและการติดตามสถานะ รวมถึงแบบสมัคร หน้าบิล งานซ่อม การจัดการผู้มาติดต่อ การแจ้งเตือน และรายงาน | Frontend regression ชุดที่ระบุในบทที่ 4 ผ่าน 136/136 กรณี แต่เป็นการทดสอบ logic และสถานะหน้าจอ ไม่ใช่ Browser Acceptance ครบทุกหน้า; มีผลผู้ใช้รายงานเฉพาะกรณีที่ระบุ |
| 5. ทดสอบส่วนสำคัญด้วยชุดทดสอบอัตโนมัติ การเชื่อมต่อ และการตรวจระบบตามขอบเขต | ดำเนินการทดสอบ Backend, Frontend, PostgreSQL integration, runtime HTTP/ฐานข้อมูล/ไฟล์ และตรวจสอบสิทธิ์ในกรณีที่ระบุ | Backend regression ชุดที่รายงานผ่าน 196/196; ชุดอื่นรายงานแยกตามตารางที่ 4.1 ไม่บวกเป็นยอดเดียว และ full `npm test` ยังมี OCR 3 กรณีที่ติดปัญหา credentials ของฐานทดสอบ จึงยังสรุปว่า full suite ผ่านทั้งหมดไม่ได้ |

นอกจากนี้ การตรวจ runtime ของกระบวนการย้ายออกและลบผู้พักทดสอบพบว่าระบบคืนห้อง ลบข้อมูลที่ผูกกับผู้พักตามรายการที่ตรวจ 16 ประเภท ตรวจไฟล์ 10 รายการ และติดตามงาน cleanup 11 งานจนเสร็จ โดยยังเก็บบัญชี User ไว้ ผลดังกล่าวเป็นหลักฐานเฉพาะข้อมูลและรายการที่ตรวจในรอบนั้น ไม่รับรองทุกชนิดไฟล์หรือทุกกรณีของการลบข้อมูล

การทดสอบโหลดแบบจำกัดในเครื่องใช้คำขอสังเคราะห์ 12 รายการ พร้อมกัน 4 คำขอ และได้ค่าประมาณ 77.67 คำขอและรายการสำเร็จต่อวินาทีในช่วงทดลองสั้น ตัวเลขนี้ไม่ใช่ผลวัดสมรรถนะของระบบ production หรือการทดสอบต่อเนื่องระยะยาว

## 5.2 อภิปรายผล

ผลการพัฒนาแสดงให้เห็นว่าการรวมข้อมูลห้อง ผู้พัก สัญญา บิล งานแจ้งซ่อม และผู้มาติดต่อไว้ในเว็บแอปพลิเคชันเดียวทำให้สามารถกำหนดความสัมพันธ์และตรวจสิทธิ์ของแต่ละกระบวนการที่ Backend และฐานข้อมูลได้ การใช้ PostgreSQL เป็นแหล่งข้อมูลหลักช่วยให้การเปลี่ยนสถานะและการตรวจสอบความสัมพันธ์ในกระบวนการสำคัญสามารถทดสอบผ่าน Integration Test ได้ ส่วน Redis ทำหน้าที่จัดการข้อมูลชั่วคราวและการควบคุมคำขอบางประเภท ไม่ใช้แทนประวัติธุรกรรมหลัก

ผล Integration ของการเลือกห้องแสดงให้เห็นว่าการตรวจความจุและจัดการคำขอพร้อมกันสามารถทดสอบด้วยฐานข้อมูลแยกได้ อย่างไรก็ตาม ผล 8/8 กรณีครอบคลุมเฉพาะเงื่อนไขที่กำหนดในชุดทดสอบ และการเชื่อมต่อบริการชำระเงินจริงยังอยู่นอกขอบเขต จึงยังใช้สรุปความถูกต้องของธุรกรรมกับธนาคารหรือผู้ให้บริการจริงไม่ได้ ในทำนองเดียวกัน การสร้าง QR หรือการบันทึกสถานะในระบบไม่ใช่หลักฐานว่ามีการโอนเงินจริง และการคืนเงินจริงยังต้องดำเนินการภายนอกระบบพร้อมบันทึกหลักฐานโดยผู้ดูแล

การแยกผลทดสอบตามระดับช่วยให้ตีความผลได้ตรงกับสิ่งที่ตรวจ Backend 196/196 และ Frontend 136/136 ยืนยันเฉพาะชุด regression ที่ระบุ ขณะที่ Integration บนฐานข้อมูลแยกยืนยันการทำงานร่วมกันของ HTTP, service และ PostgreSQL ในกรณีที่กำหนด ส่วนผล runtime และการรายงานจากผู้ใช้มีขอบเขตของตนเอง การนำจำนวนทั้งหมดมารวมเป็นตัวเลขเดียว หรือเรียกว่าเป็นจำนวน flow ที่ผ่านทั้งหมด จะทำให้เข้าใจเกินกว่าหลักฐานที่มี

OCR และ Face Verification เป็นจุดเชื่อมต่อบริการภายนอก ระบบจึงควบคุมการตรวจข้อมูล การยืนยันความเป็นเจ้าของ และการจัดการข้อผิดพลาดได้ แต่คุณภาพการอ่านข้อความหรือการเปรียบเทียบใบหน้าขึ้นกับบริการและข้อมูลทดสอบด้วย ผล Face 3 จาก 4 ภาพที่ตรงตามที่คาดคิดเป็นร้อยละ 75 เฉพาะชุดทดลองดังกล่าว ไม่ใช่ค่า accuracy ที่ใช้แทนประชากรหรือสภาพแวดล้อมทั่วไป ส่วน OCR ยังไม่มีชุดภาพพร้อมคำตอบจริงรายฟิลด์ จึงยังคำนวณเป็นเปอร์เซ็นต์ไม่ได้

## 5.3 ปัญหาและอุปสรรคในการดำเนินงาน

ระหว่างพัฒนาพบปัญหาที่เกี่ยวข้องกับเงื่อนไขหลายชั้นและการเชื่อมต่อระหว่างส่วนต่าง ๆ สรุปปัญหา แนวทางจัดการ และสถานะหลักฐานได้ดังตารางที่ 5.2

**ตารางที่ 5.2 ปัญหาและอุปสรรคในการดำเนินงาน**

| ปัญหาหรืออุปสรรค | แนวทางจัดการ | ผลและข้อควรระวัง |
|---|---|---|
| แบบสมัครบันทึก draft ได้ แต่ไม่สามารถสร้าง QR หรือส่งใบสมัครต่อได้เมื่อเงื่อนไขสัญญาของผู้ดูแลไม่ครบ | ตรวจเงื่อนไขสัญญาที่ Backend และให้ผู้ดูแลกำหนดข้อมูลที่จำเป็นก่อนดำเนินขั้นต่อไป | ช่วยแยกสาเหตุด้านการตั้งค่าออกจากการกรอกแบบสมัคร แต่ยังต้องทดสอบกับ deployment และการตั้งค่าจริงก่อนใช้งาน |
| การหมดเวลาถือสิทธิ์ห้องและยอดเครดิตอาจทำให้ผู้สมัครเข้าใจว่าเงินถูกยกเลิกหรือคืนแล้ว | แยกเวลาถือสิทธิ์ห้องออกจากสถานะเครดิต อธิบายยอดส่วนเกิน และแยกคำขอคืนเครดิตออกจากการบันทึกคืนเงินจริง | การคืนเงินจริงไม่เกิดขึ้นอัตโนมัติ และ flow คำขอคืนที่เพิ่มล่าสุดยังไม่มีผล Browser Acceptance และ Integration ครบชุดหลังเพิ่มฟังก์ชัน |
| การลบผู้พักมีข้อมูลสัมพันธ์ ไฟล์ และงาน cleanup ภายนอกที่ต้องจัดการให้สอดคล้องกัน | ใช้ guarded purge ตรวจข้อมูลที่เกี่ยวข้อง เก็บบัญชี User และติดตามงานล้างไฟล์ด้วยสถานะ cleanup | มีผล runtime เฉพาะข้อมูลทดสอบที่ตรวจแล้ว; ต้องทดสอบเพิ่มกับไฟล์และธุรกรรมหลายรูปแบบ รวมทั้งกรณีบริการภายนอกขัดข้อง |
| บริการ OCR, Face และการส่ง OTP อาจไม่พร้อมใช้งานหรือให้ผลไม่ครบ | จัดการ timeout/error และเปิดให้ retry ตาม flow ที่ระบบรองรับ พร้อมใช้ mock ในชุดทดสอบที่ระบุ | การทดสอบ mock ไม่ยืนยันความพร้อม คุณภาพ หรือเวลาตอบสนองของผู้ให้บริการจริง |
| ผลทดสอบจากหลายรอบใช้ฐานข้อมูลและขอบเขตต่างกัน | แยกประเภทหลักฐาน วันที่ และชุดทดสอบในรายงาน; ไม่รวมยอดเป็นจำนวนเดียว | full `npm test` ยังมี OCR 3 กรณีที่ต้องแก้ credentials ของฐานทดสอบและรันซ้ำก่อนสรุปผลครบทุกชุด |

## 5.4 ข้อจำกัดของโครงงาน

1. โครงงานเป็นระบบต้นแบบและผลทดสอบยืนยันเฉพาะกรณี สภาพแวดล้อม และวันที่ที่ระบุในบทที่ 4 ยังไม่มีการประเมินการใช้งานระยะยาวใน production หรือการประเมินความพึงพอใจจากกลุ่มผู้ใช้ด้วยวิธีทางสถิติ
2. ยังไม่ได้เชื่อมต่อหรือรับรองการทำงานของกล้องวงจรปิด อุปกรณ์ Edge และชุดควบคุมประตูจริง การสั่งประตูหรือการบันทึกโดยเจ้าหน้าที่ในระบบไม่ใช่หลักฐานว่าประตูจริงเปิดหรือปิด
3. การเชื่อมต่อ OCR, Face Verification, การชำระเงิน, การแจ้งเตือน และ SMS กับผู้ให้บริการจริงยังไม่ได้รับการยืนยันครบวงจร ผลจาก mock ยืนยันเฉพาะพฤติกรรมของระบบภายใต้คำตอบจำลอง
4. ยังไม่มีชุดข้อมูล OCR ที่มีคำตอบอ้างอิงรายฟิลด์ จึงไม่สามารถรายงานความแม่นยำ OCR ได้ ส่วนผล Face มีเพียง 4 ภาพ โดย 3 ภาพตรงตามที่คาดและ 1 ภาพตรวจไม่พบใบหน้า ซึ่งไม่เพียงพอสำหรับสรุปความแม่นยำโดยรวม และไม่มีการประเมิน liveness หรือการป้องกันภาพถ่าย/วิดีโอ
5. ผลทดสอบโหลดเป็นการทดลองช่วงสั้นในเครื่อง ไม่ครอบคลุมเครือข่าย ผู้ให้บริการภายนอก ปริมาณผู้ใช้สูง หรือการทำงานต่อเนื่อง จึงไม่ใช่ SLA หรือข้อรับรองขีดความสามารถ production
6. การเพิ่ม flow คำขอคืนเครดิตและการยินยอมมีผลทดสอบบางส่วน แต่ยังขาด Browser Acceptance และการตรวจครบทุกสถานการณ์หลัง deploy; นอกจากนี้ การถอนความยินยอมยังไม่มี endpoint อัตโนมัติ
7. การทดสอบ backup/restore และการทำงานของนโยบายเก็บรักษาข้อมูลรายปีในสภาพแวดล้อมใช้งานจริงยังไม่ปรากฏเป็นหลักฐานในผลที่รายงาน

## 5.5 ข้อเสนอแนะ

1. แก้การตั้งค่า credentials ของฐานทดสอบ OCR แล้วรัน full test suite ซ้ำ พร้อมบันทึกคำสั่ง สภาพแวดล้อม วันที่ และผลแยกตามชุด เพื่อให้รายงานผลครบและทำซ้ำได้
2. ทดสอบ Browser Acceptance ของ flow สมัคร การหมดเวลาถือสิทธิ์ห้อง การใช้เครดิต การขอคืนเครดิต การคืนเงินจริงโดยผู้ดูแล และการยินยอม หลัง deploy ในสภาพแวดล้อมทดสอบ โดยใช้บัญชีและข้อมูลสมมติ
3. หากต้องรายงานความแม่นยำ OCR ให้จัดทำชุดเอกสารที่ได้รับอนุญาตและคำตอบอ้างอิง แยกชุดพัฒนาและชุดทดสอบ แล้วกำหนดวิธีนับผลถูกต้องรายฟิลด์ก่อนคำนวณ หากประเมิน Face ให้กำหนดผู้เข้าร่วมที่ยินยอม จำนวนภาพแยกตามบุคคล threshold และนิยามผล 1:1 หรือ 1:N ล่วงหน้า
4. ก่อนใช้งานร่วมกับกล้อง ประตู SMS หรือผู้ให้บริการภายนอก ควรทดสอบการเชื่อมต่อจริง การหมดเวลา การลองซ้ำ การป้องกันคำขอซ้ำ และกรณีบริการขัดข้องแยกจากผล mock พร้อมระบุชัดว่าอะไรทำงานอัตโนมัติและอะไรต้องให้ผู้ดูแลดำเนินการ
5. ทดสอบการสำรองและกู้คืนฐานข้อมูลกับไฟล์ รวมถึงการติดตามงาน cleanup และการเก็บรักษาข้อมูลในสภาพแวดล้อมแยกก่อนกำหนดนโยบายใช้งานจริง พร้อมทบทวนสิทธิ์เข้าถึง ความปลอดภัยของ secret และการเปิดพอร์ตตาม deployment
6. หากต้องการประเมินประโยชน์ต่อผู้ใช้ ควรกำหนดกลุ่มตัวอย่าง งานที่ให้ทดลอง และแบบประเมินก่อนเก็บข้อมูล แล้วรายงานจำนวนผู้เข้าร่วมและวิธีวิเคราะห์ ไม่ควรอนุมานความพึงพอใจจากจำนวนชุดทดสอบหรือคำยืนยันที่ไม่มีแบบประเมินรองรับ
7. จัดทำภาพประกอบจากระบบด้วยข้อมูลทดสอบ ปกปิดข้อมูลส่วนบุคคลและหลักฐานชำระเงินจริง และตรวจชื่อภาพ คำบรรยายใต้ภาพ ตาราง และรูปแบบการอ้างอิงให้ตรงกับข้อกำหนดของหลักสูตร

ข้อเสนอแนะข้างต้นมุ่งปิดช่องว่างระหว่างระบบต้นแบบกับการประเมินที่ทำซ้ำได้ โดยการขยายระบบไปยังอุปกรณ์หรือบริการจริงควรดำเนินการเมื่อมีสภาพแวดล้อม ผู้ให้บริการ และแนวทางคุ้มครองข้อมูลที่พร้อม
