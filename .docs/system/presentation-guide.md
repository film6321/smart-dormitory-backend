# แนวทางนำเสนอสอบโครงงาน MEEDEE Dormitory

จัดทำ 14 ตุลาคม 2569 จากข้อกำหนดสอบที่ผู้ใช้ให้และหลักฐานในเอกสารระบบ ใช้เป็นโครงทำสไลด์และซ้อมพูด ยังไม่ใช่ไฟล์ PowerPoint และยังไม่มีภาพหน้าจอแนบ

## 1. สิ่งที่ต้องเตรียมตามข้อกำหนดสอบ

| เรื่อง | สิ่งที่ต้องทำ |
|---|---|
| เวลาไปถึง | ถึงก่อนเวลาสอบอย่างน้อย 10 นาที; เผื่อเวลาต่อเครื่องและเปิดไฟล์ด้วย |
| กลุ่มที่มีบางคนหรือทั้งกลุ่มไปสหกิจ | เตรียมรายงานบทที่ 1–5 |
| กลุ่มที่ทำโปรเจกต์ 2 ต่อทั้งกลุ่ม | เตรียมรายงานบทที่ 1–4 รวมผลทดลองบางส่วน |
| รายงานกรรมการ | เตรียม 4 ฉบับ เนื้อหาและรุ่นเอกสารตรงกัน |
| นำเสนอ | 10 นาที เรียงบทที่ 1 → 2 → 3 → 4 → 5 |
| ตอบคำถาม | 10 นาที เตรียมหลักฐานสำหรับเปิดตอบเพิ่มเติม |
| วิธีพูด | อธิบายจากภาพและประเด็นสำคัญ ไม่อ่านย่อหน้าบนสไลด์ |

เลือกชุดรายงานตามสถานะจริงของกลุ่ม ไม่สรุปจากการที่มีไฟล์ครบ 5 บทแล้ว หากกลุ่มส่งบท 1–4 ให้ใช้ช่วงท้ายเสนอข้อสรุปผลที่มีและแผนงานต่อ แทนการอ้างว่าบท 5 ผ่านข้อกำหนดแล้ว โดยตรวจรูปแบบกับอาจารย์ผู้รับผิดชอบก่อนพิมพ์

## 2. เรื่องหลักที่กรรมการควรเข้าใจ

ระบบเชื่อมการสมัครเข้าพัก ห้อง สัญญา การชำระเงิน งานซ่อม และผู้มาติดต่อเข้าด้วยกัน ผู้พักทำรายการของตนเอง ผู้ดูแลจัดการและตรวจสถานะ ส่วนข้อมูลกับสถานะสำคัญอยู่ในฐานข้อมูล ทำให้ติดตามงานต่อและตรวจการล้างข้อมูลได้

เลือกย้ำผลงาน 3 ประเด็น:

1. สมัคร 4 ขั้น ใช้ข้อมูลเดิมต่อถึงสัญญา และกู้ฉบับร่างกับยอดชำระหลังรีเฟรชได้
2. งานมีปลายทางชัดเจน เช่น ผู้พักยืนยันปิดงานซ่อม และผู้ดูแลตรวจสถานะรวม
3. ควบคุมสิทธิ์ ความยินยอม และการลบข้อมูลที่ผูกผู้พัก โดยบัญชียังสมัครใหม่ได้

ใช้ปัญหาจากการพัฒนาและตรวจระบบเป็นตัวอย่าง ไม่อ้างว่ามีผลสำรวจหอพักหรือการสัมภาษณ์ผู้ใช้ หากยังไม่มีหลักฐานนั้น

## 4. เนื้อหาและแนวพูดรายสไลด์

### หน้า 1 — ชื่อโครงงานและปัญหา

**บนสไลด์:** ชื่อระบบ ผู้จัดทำ และภาพเดียวที่สื่อว่าข้อมูลสมัคร ห้อง บิล และงานซ่อมต้องเชื่อมกัน ข้อความปัญหาไม่เกิน 3 ข้อ

**แนวพูด:** “โครงงานนี้พัฒนาระบบบริหารจัดการหอพัก MEEDEE Dormitory ให้ผู้พักและผู้ดูแลทำงานบนข้อมูลชุดเดียวกัน ประเด็นที่แก้คือการกรอกข้อมูลซ้ำ สถานะงานไม่ต่อเนื่อง และข้อมูลที่ยังค้างหลังลบผู้พัก วันนี้จะนำเสนอแนวคิด การออกแบบ และผลทดสอบตามลำดับบทครับ/ค่ะ”

ที่มา: [บทที่ 1](01-introduction.md)

### หน้า 2 — วัตถุประสงค์และขอบเขต

**บนสไลด์:** ผู้ดูแล / ผู้พัก / ผู้มาติดต่อ พร้อมหน้าที่หลักคนละ 1 บรรทัด และวัตถุประสงค์ 3 ข้อ ได้แก่ รวมงานหอพัก ลดการกรอกซ้ำ และติดตามสถานะ/ตรวจข้อมูลได้

**แนวพูด:** “ผู้พักสมัคร ชำระบิลและแจ้งซ่อม ผู้ดูแลจัดห้อง ตรวจใบสมัครและติดตามงาน ส่วนผู้มาติดต่อส่งคำขอเข้าพบ ขอบเขตที่ตรวจในรอบนี้คือเว็บ API ฐานข้อมูลและไฟล์ ส่วนกล้อง ประตู SMS และบริการภายนอกจริงยังไม่ใช้เป็นผลรับรองของรอบทดสอบนี้”

ใส่ขอบเขตที่ยังไม่ตรวจเป็นแถบสั้น ๆ ไม่ใช้พื้นที่ครึ่งสไลด์ และไม่กล่าวว่าถอดการเชื่อมต่อเหล่านั้นออกจากระบบแล้ว

### หน้า 3 — แนวคิดและเทคโนโลยี

**บนสไลด์:** ตารางสั้นหรือภาพ 4 กลุ่ม: พัฒนาเว็บด้วย TypeScript/React/Express, เก็บข้อมูลด้วย PostgreSQL/Prisma, งานชั่วคราวด้วย Redis, จัดบริการด้วย Docker Compose

**แนวพูด:** “เลือกจัดโครงสร้างตามงาน เช่น ผู้พัก บิล และซ่อม เพื่อดูแลกฎแต่ละส่วนได้ชัดเจน PostgreSQL เก็บข้อมูลหลัก Redis ใช้ cache และล็อกชั่วคราว ส่วน OCR และใบหน้าเรียกผ่านบริการที่เชื่อมต่อ ไม่ได้สร้าง engine ขึ้นใหม่ในโครงงานนี้”

ไม่ไล่รายชื่อทุก package แยกประเภทให้ถูก: TypeScript เป็นภาษา React เป็น UI library Express เป็น web framework และ Vite เป็นเครื่องมือพัฒนา/build

ที่มา: [บทที่ 2](02-background-and-methods.md), [เทคโนโลยีหลัก](deployment-and-data.md)

### หน้า 4 — ออกแบบภาพรวมและข้อมูล

**บนสไลด์:** แผนภาพระบบเดียว แสดงผู้ใช้งาน → เว็บ/API → ฐานข้อมูล/ไฟล์ และความสัมพันธ์ User → Tenant → Room, Bill และ MaintenanceTicket

**แนวพูด:** “เราแยกบัญชี User ออกจากข้อมูลการเข้าพัก Tenant บัญชีจึงยังอยู่เมื่อย้ายออกและลบโปรไฟล์ ห้อง บิล และงานซ่อมเชื่อมกับการเข้าพัก ทำให้ตรวจสิทธิ์และติดตามข้อมูลที่ต้องลบได้”

ใช้เฉพาะข้อมูลหลักในภาพ ไม่ใส่ทุกตารางใน ER บนสไลด์เดียว เก็บ ER ละเอียดเป็นสไลด์สำรอง และไม่วาดตาราง Building/Course ที่ไม่มีใน schema จริง

ที่มา: [บทที่ 3](03-system-design.md)

### หน้า 5 — ออกแบบ flow

**บนสไลด์:** รับทราบ/ยินยอมข้อมูลสมัคร → สมัคร 4 ขั้น → ผู้ดูแลอนุมัติ → ใช้งานระหว่างพัก → ย้ายออก/ลบข้อมูล ส่วนบันทึกใบหน้ามีจุดยินยอมแยก

**แนวพูด:** “ก่อนเริ่มสมัครมีคำชี้แจงข้อมูลส่วนบุคคล จากนั้นตรวจตัวตนและข้อมูลส่วนตัว กรอกผู้ติดต่อ เลือกห้องและชำระเงิน แล้วตรวจสัญญาก่อนยื่น ข้อมูลตัวตนส่งต่อถึงสัญญา ไม่ต้องกรอกใหม่ การตรวจชำระกับการอนุมัติเข้าพักเป็นคนละสถานะ”

จุดยินยอมอยู่ก่อน flow ไม่เรียกเป็นขั้นที่ 5 ของใบสมัคร และไม่รวมการยินยอมใบหน้ากับการยอมรับสัญญา

ที่มา: [ผู้พักและสัญญา](users-and-tenants.md), [การชำระเงิน](billing-and-payments.md)

### หน้า 6 — ผลพัฒนาการสมัครและการกู้ข้อมูล

**บนสไลด์:** ภาพหน้าสมัครที่ตรวจแก้ข้อมูล กับภาพสัญญาหรือยอดชำระเดิม ใช้เลขกำกับว่า “กรอกครั้งแรก → นำไปใช้ต่อ → รีเฟรชทำต่อได้”

**แนวพูด:** “ข้อมูลที่อ่านจากบัตรให้ผู้สมัครตรวจแก้ก่อนนำไปใช้ในสัญญา ระบบเก็บฉบับร่างและเครดิตที่ตรวจผ่านไว้กับบัญชี เมื่อรีเฟรชจึงกลับมาทำต่อได้ การเปลี่ยนห้องคำนวณยอดขาดจากยอดเดิม และยังต้องผ่านกฎการตรวจชำระ ไม่ถือว่าสร้าง QR แล้วแปลว่าจ่ายสำเร็จ”

ใช้ภาพข้อมูลทดสอบ ปิดข้อมูลบัตรและสลิปจริง ไม่โอนเงินสดหรือเริ่มสมัครใหม่ทั้ง flow ระหว่างนำเสนอ 10 นาที หากใช้คลิปสาธิตสั้นให้รวมไว้ใน 75 วินาทีของหน้านี้

### หน้า 7 — ผลพัฒนางานผู้ดูแลและงานซ่อม

**บนสไลด์:** ภาพ Dashboard ที่อ่านตัวเลขได้ และเส้นสถานะงานซ่อม PENDING → APPROVED → IN_PROGRESS → RESOLVED → CLOSED

**แนวพูด:** “ผู้ดูแลเห็นภาพรวมห้อง บิลและกิจกรรมล่าสุด งานซ่อมแยกซ่อมเสร็จออกจากปิดงาน ผู้พักเป็นผู้ยืนยันขั้นสุดท้าย ผลที่ตรวจจริงมีงานทดสอบที่ผู้พักยืนยัน CLOSED แล้ว ส่วนการแจ้งเตือนแยกตามสิทธิ์และบัญชี”

ผู้มาติดต่อให้กล่าวเพิ่มเพียง 1 ประโยคว่า “ผู้มาติดต่อส่งคำขอและดาวน์โหลดหลักฐาน PNG ได้ ส่วนการเข้าพบและข้อมูลของคนอื่นถูกจำกัดสิทธิ์” เก็บภาพและ flow ละเอียดไว้ตอบคำถาม

ที่มา: [งานซ่อม](maintenance.md), [Dashboard/รายงาน](reports-and-audit.md), [ผู้มาติดต่อ](visitors.md)

### หน้า 8 — ข้อมูลส่วนบุคคลและการล้างข้อมูล

**บนสไลด์:** ความยินยอม 2 กล่อง HOUSING / FACE_ENROLLMENT และตารางสั้น “ข้อมูล/ไฟล์ผู้พักถูกล้าง — บัญชี User ยังอยู่”

**แนวพูด:** “ใบสมัครและใบหน้าใช้ความยินยอมคนละวัตถุประสงค์ บันทึกบัญชี รุ่นข้อความ และเวลาไว้ในฐานข้อมูล ก่อนเก็บภาพระบบตรวจหลักฐานอีกครั้ง ส่วนการลบผู้พักตรวจทั้งฐานข้อมูล ไฟล์และคิวล้าง ผลทดสอบเดิมล้างไฟล์ 10 รายการและคิว 11 งานสำเร็จ โดยบัญชียังสมัครใหม่ได้”

แยกผลให้ชัด: การลบเป็น runtime ที่ตรวจไว้ก่อนหน้า ส่วนหน้าความยินยอมใหม่ผ่าน automated tests และ smoke แต่ยังรอการตรวจผ่านหน้าจอจริง ไม่อ้างว่าลบภาพใบหน้าจริงผ่านแล้ว เพราะบัญชีทดสอบรอบนั้นไม่มีภาพใบหน้า และไม่อ้างว่าเพิ่ม checkbox แล้วผ่าน PDPA ครบทุกด้าน

ที่มา: [ผู้พักและการลบ](users-and-tenants.md), [ใบหน้า](face-verification.md)

### หน้า 9 — ผลทดสอบ

**บนสไลด์:** ตาราง 3 แถวต่อไปนี้ พร้อมวันที่และชนิดหลักฐาน

| ชุดหลักฐาน | ผลที่ใช้บนสไลด์ | ความหมาย |
|---|---|---|
| กฎธุรกิจ/API unit และ mock วันที่ 14 ต.ค. 2569 | 185/185 ผ่าน | กรณีที่กำหนดใน suite ไม่ใช่ทุก flow ผ่านหน้าจอ |
| Logic/สถานะหน้าจอ unit/VM วันที่ 14 ต.ค. 2569 | 119/119 ผ่าน | รวมความยินยอม กดซ้ำ รีเฟรชและยกเลิกคำขอ |
| Runtime ที่บันทึกก่อนหน้า | ชำระบิล → ปิดงานซ่อม → ย้ายออก/ลบ → สมัครใหม่ | API/DB/files และการยืนยันผู้ใช้ตามรายการในรายงาน |

**แนวพูด:** “ทดสอบทั้งกฎธุรกิจ การตรวจสิทธิ์ และการจัดการสถานะหน้าจอ รวมถึง flow ที่ตรวจ API ฐานข้อมูลและไฟล์ ผล suite ล่าสุดผ่านตามจำนวนนี้ แต่ไม่ได้ใช้แทนผลอุปกรณ์หรือ provider จริง สิ่งที่เน้นตรวจเป็นพิเศษคือการกรอกซ้ำ การส่งซ้ำ และข้อมูลตกค้างหลังลบ”

หากแสดงร้อยละ ให้ระบุว่าเป็นสัดส่วนกรณีทดสอบในชุดที่ผ่าน ไม่เรียกว่า accuracy หรือความปลอดภัย 100% ชุด integration 38/38, 27/27 และ 29/29 เป็นคนละรอบ เก็บในภาคสำรอง ไม่บวกเป็นการรันครั้งเดียว

## 7. วิธีซ้อมและแบ่งการพูด

1. รอบแรกเล่าจากหัวข้อให้เข้าใจ ก่อนปรับให้ตรงเวลา อัดเสียงฟังว่ามีคำเทคนิคที่ไม่อธิบายหรือไม่

4. หากนำเสนอหลายคน ให้แบ่งช่วงตามบทและส่งต่อประโยคเดียว ตกลงล่วงหน้าว่าใครรับคำถามเรื่องข้อมูล สิทธิ์ และการทดสอบ ไม่กำหนดจำนวนผู้พูดจนกว่าจะทราบสมาชิกจริง
5. ให้เพื่อนถามจากตารางข้อ 6 ตอบประมาณ 30–45 วินาทีต่อคำถาม และเปิดสไลด์สำรองเฉพาะเมื่อช่วยยืนยันคำตอบ

โพยผู้พูดต่อหน้าใช้เพียง “ประเด็นหลัก → ตัวอย่าง → ผล” ไม่คัดแนวพูดทั้งหมดไปใส่ในสไลด์ ขณะพูดให้อธิบายว่าภาพแสดงอะไรและแก้ปัญหาอย่างไร

| 7 | บิลและค่าใช้จ่าย | ส่วนทางเลือกของสไลด์ 5 หน้า 3–4 | ตรงบางส่วน คำว่าไม่ได้เชื่อม Payment Gateway กว้างเกินไป เพราะมี Payment API wrapper ควรบอกว่าระบบสร้าง QR และตรวจสลิปผ่านบริการภายนอก โดยไม่อ้างการเชื่อมธนาคารหรือ settlement จริงครบระบบ |
| 8 | แจ้งซ่อมและผู้มาติดต่อ | ส่วนทางเลือกของสไลด์ 5 หน้า 4 | ตรง แต่ยังไม่อธิบายปลายทางงานซ่อมและคำขอผู้มาติดต่อ เพิ่มผู้พักยืนยันปิดงาน และแยกสถานะคำขอจากการเข้าพบ WAITING/ADMITTED/COMPLETED; แทนข้อความ “เอาภาพมาใส่” ด้วยภาพจริงที่ปิดข้อมูลส่วนตัว |
| 9 | OCR | สไลด์ 6 หน้า 5 | ตรงที่สุด ลำดับภาพ → อ่าน → เติม → ตรวจแก้ถูกต้อง เพิ่มว่าระบบส่งภาพไป OCR API ภายนอก และแทน placeholder ด้วยตัวอย่างข้อมูลทดสอบ |
| 10 | Face Recognition และการเข้าออก | สไลด์ 7 หน้า 5 | ลำดับตรวจจับ/จัดแนว/embedding/เปรียบเทียบสอดคล้องในเชิงอธิบายบริการ แต่ภาพกล่าวว่า “ปลอดภัยและแม่นยำ” เกินหลักฐาน และคำว่าตัดสินใจเข้าออกอาจทำให้เข้าใจว่าเปิดประตูจริงผ่านแล้ว เปลี่ยนเป็นผลตรวจเทียบเกณฑ์และบันทึกเหตุการณ์ พร้อมระบุอุปกรณ์จริงนอกขอบเขต QA |
| 11 | เทคโนโลยีที่ใช้พัฒนา | สไลด์ 8 หน้า 6 | ไม่ตรงกันตรงช่อง Backend: สไลด์ใส่ React/TypeScript/Vite แต่สคริปต์ใช้ Node.js/Express ซึ่งตรงกับระบบกว่า แยก PostgreSQL ฐานข้อมูลหลักออกจาก Redis cache และระบุ Python/FastAPI/OpenCV/InsightFace เป็นเครื่องมือของบริการภายนอกเฉพาะที่ตรวจยืนยันได้ |

| 13 | ผลการพัฒนาและข้อจำกัด | สไลด์ 10 หน้า 6 | ตรงแต่กว้าง ควรเปลี่ยนจาก “ออกแบบระบบ” เป็นสิ่งที่พัฒนาและตรวจได้ เช่น กู้ draft/เครดิต ปิดงานซ่อม และลบแล้วสมัครใหม่ได้ พร้อมระบุว่าไม่มีผล accuracy หรือประตู/provider จริงครบระบบ ลบหัวข้อ SYSTEM TESTING ที่ซ้ำจากหน้าก่อน |
| 14 | สรุปผล | สไลด์ 11 หน้า 7 | ตรงบางส่วน สไลด์มีงานต่อยอดความปลอดภัย/อัตโนมัติ แต่สคริปต์ไม่มี ต้องแยกเป็นข้อเสนอแนะ และใช้คำว่า “ช่วยลดการกรอกซ้ำ” แทนการอ้างผลลดเวลา/ขั้นตอนเชิงตัวเลขที่ยังไม่ได้วัด |

### 9.3 ข้อความที่ควรแก้ก่อนซ้อม

**การชำระเงิน — หน้า 7 / สคริปต์หน้า 3–4**

ใช้แนวพูด: “ผู้ดูแลสร้างบิลจากค่าเช่าและค่าสาธารณูปโภค ผู้พักสร้าง QR และแนบสลิป ระบบส่งตรวจผ่าน Payment API และบันทึกสถานะไว้ การสร้าง QR ยังไม่หมายถึงชำระสำเร็จ และการทดสอบบริการภายนอกจริงแยกจากผลทดสอบ API ของระบบ”

การไม่ได้เชื่อมธนาคารโดยตรงกับการไม่มีบริการตรวจชำระเป็นคนละเรื่อง จึงไม่ควรใช้ประโยคปฏิเสธรวมว่าไม่มี Payment Gateway แล้วจบคำอธิบาย

**การตรวจใบหน้า — หน้า 10 / สคริปต์หน้า 5**

ใช้แนวพูด: “ระบบหอพักเชื่อมบริการตรวจใบหน้าภายนอก โดยบริการเปรียบเทียบข้อมูลกับใบหน้าที่ลงทะเบียน แล้วระบบนำผลมาตรวจสิทธิ์และบันทึกเหตุการณ์ รอบนี้ตรวจส่วนเว็บ API และการจัดการข้อมูล ยังไม่รับรองความแม่นยำหรือการเปิดประตูจากอุปกรณ์จริง”

เปลี่ยนคำอธิบายบนสไลด์จาก “อย่างปลอดภัยและแม่นยำ” เป็น “รับผลตรวจใบหน้าเพื่อประกอบการตรวจสิทธิ์และบันทึกเหตุการณ์” คะแนนผ่าน threshold ไม่ใช่ accuracy ของระบบ และต้องแยกความยินยอม FACE_ENROLLMENT ก่อนเก็บภาพ

**เทคโนโลยี — หน้า 11 / สคริปต์หน้า 6**

จัดตามหน้าที่ในระบบเดียว เช่น ภาษา TypeScript; Runtime Node.js; Framework Express; UI React; เครื่องมือ build Vite; ฐานข้อมูล PostgreSQL; ORM Prisma; cache Redis; สื่อสาร Axios/Socket.IO; ติดตั้ง Docker/Compose และ Nginx ไม่จำเป็นต้องนำทุกตัวไปพูด รายละเอียดอยู่ใน [ตารางเทคโนโลยี](deployment-and-data.md#เทคโนโลยีหลัก-แยกตามประเภท)

AI Services ให้แสดงเป็น “OCR API / Face API ที่ระบบเชื่อมต่อ” ก่อน หากจะใส่ stack ภายในบริการให้ตรวจ source ของบริการนั้นแยกอีกครั้ง การมีไฟล์โมเดลหรือรายชื่อในสไลด์ไม่ใช่หลักฐานว่าใช้งานโมเดลนั้นอยู่

**ผลทดสอบ — หน้า 12–13 / สคริปต์หน้า 6**

ใช้แนวพูด: “ผลที่บันทึกวันที่ 14 ตุลาคม 2569 ชุดกฎธุรกิจ/API ผ่าน 185 จาก 185 กรณี และ logic/สถานะหน้าจอผ่าน 119 จาก 119 กรณี ทั้งสองเป็น unit/mock ตามชุดที่กำหนด ส่วน flow ที่ตรวจจริงมีผล API ฐานข้อมูล ไฟล์ และการยืนยันผู้ใช้แยกกัน ไม่ใช้จำนวนนี้แทนผลทุกหน้าจอหรือ provider จริง”

ตารางผลบนสไลด์ควรมี “กรณี / ผล / ชนิดหลักฐาน / วันที่” พร้อมตัวอย่างปลายทาง เช่น ผู้พักยืนยันปิดงาน และลบผู้พักแล้วสมัครใหม่ได้ อ้าง [บทที่ 4](04-implementation-and-results.md) ไม่เปลี่ยนวันที่ผลเก่าเป็นวันนำเสนอ และไม่รวมตัวเลขต่างชุดเป็นการทดสอบครั้งเดียว

### 9.5 ลำดับบทและเวลา

ลำดับปัจจุบันยังไม่เรียงบท 1–5 ชัด เพราะผลฟังก์ชันอยู่หน้า 6–10 แต่เทคโนโลยีบท 2 อยู่หน้า 11 และออกแบบฐานข้อมูลบท 3 ปนผลทดสอบบท 4 อยู่หน้า 12 ควรจัดใหม่เป็น บท 1 ปัญหา/วัตถุประสงค์/ขอบเขต → บท 2 แนวคิด/เทคโนโลยี → บท 3 ภาพรวม/ERD/flow → บท 4 ภาพผลพัฒนาและผลทดสอบ → บท 5 สรุป/ข้อจำกัด/ข้อเสนอแนะ

ใช้โครง 10 หน้าหลักในข้อ 3 ของคู่มือนี้ได้ แล้วเก็บ OCR/ใบหน้า/ERD ละเอียดเป็นสไลด์สำรอง ไม่จำเป็นต้องลดให้เหลือ 10 หน้าตายตัว หากคง 14 หน้าต้องทำสคริปต์ 14 ช่วงให้ตรงหน้า และซ้อมจับเวลารวม 10 นาทีจริง ผลตรวจไฟล์ยังไม่ยืนยันระยะเวลาพูด เพราะสคริปต์มีข้อความทางเลือกและโพยที่ต้องตัดสินใจก่อน

### 9.6 สิ่งที่ต้องทำก่อนใช้ฉบับสอบ

1. แก้เทคโนโลยีช่อง Backend และบทบาท Redis; ตรวจรายชื่อเครื่องมือของบริการภายนอกก่อนใช้
2. แก้คำกล่าวเรื่องใบหน้าและการชำระให้ตรง wrapper และขอบเขตผลทดสอบ
3. จัดลำดับตามบท และตั้งหัวข้อสคริปต์ให้ตรงหน้าสไลด์ที่เลือกใช้จริง
4. แทน placeholder หน้า 8, 9 และ 12 ด้วยภาพงานซ่อม/ผู้มาติดต่อ, OCR และ ERD ตามหัวข้อ ไม่ใช้ภาพ OCR ในหน้าฐานข้อมูลแทน ERD
5. เพิ่ม flow สมัคร/สัญญา/กู้ยอดเดิม และตารางผลทดสอบที่มีหลักฐาน แทนรายการฟังก์ชันอย่างเดียว
6. ลบโพยและข้อความทางเลือกออกจากฉบับพูด เติมข้อมูลหน้าปก ปิดข้อมูลส่วนตัว และซ้อมจับเวลา

การตรวจครั้งนี้ไม่ตรวจความถูกต้องของชื่อผู้จัดทำหรือข้อมูลสถานศึกษาจากแหล่งภายนอก และไม่ถือคำในสไลด์ว่าเป็นหลักฐานผลวิจัยหรือผลทดสอบเพิ่มเติม

### 9.7 เนื้อหาปรับใหม่สำหรับหน้า 12–14

ข้อกำหนดหลังทบทวนกับผู้ใช้: หน้า 12 ใช้ผลทดสอบพร้อมกรณีและผลที่ยืนยันแล้ว หน้า 13 อธิบายจุดเด่นและข้อจำกัด หน้า 14 สรุปผลตามวัตถุประสงค์ ใช้ข้อความในส่วนนี้แทนแนวทางของสามหน้าเดิมในข้อ 9.2 โดยเลขหน้ายังอ้าง PDF เดิม หากจัดลำดับตามบทใหม่ต้องปรับเลขหน้าสคริปต์ตามด้วย นี่เป็นเนื้อหาสำหรับนำไปจัดสไลด์ ยังไม่ได้แก้ PDF ต้นฉบับ

**หน้า 12 — ผลการทดสอบระบบ**

หน้านี้ตอบว่า “ตรวจอะไร และได้ผลอย่างไร” ย้าย ERD ไปช่วงออกแบบระบบหรือสไลด์สำรอง แทน placeholder เดิมด้วยตารางต่อไปนี้ โดยไม่ใส่ terminal หรือรายการ tests ทั้งหมด

| กรณีที่ตรวจ | ผลที่บันทึก | ประเภทหลักฐาน |
|---|---|---|
| กฎธุรกิจและ API | ผ่าน 185/185 กรณี — 14 ต.ค. 2569 | Unit/mock และ route checks |
| Logic และสถานะหน้าจอ | ผ่าน 119/119 กรณี — 14 ต.ค. 2569 | VM/mock ไม่ใช่ browser ทุกหน้า |
| งานซ่อมจนถึงขั้นปิดงาน | ผู้พักยืนยันปิดงานทดสอบแล้ว | Runtime และการยืนยันผู้ใช้ |
| ย้ายออก ลบข้อมูล และสมัครใหม่ | ข้อมูลที่ตรวจ 16 ประเภทไม่เหลือ ไฟล์ลบ 10/10 คิวสำเร็จ 11/11; User ยังอยู่และผู้ใช้ยืนยันสมัครใหม่ได้ | API/DB/files และการยืนยันผู้ใช้ |

ข้อความกำกับใต้ตาราง: “ผลตามชุดทดสอบและ flow ที่บันทึกไว้ ไม่ใช่การรับรองทุกกรณี อุปกรณ์จริง หรือ provider ภายนอกจริงครบระบบ” ตัวเลขแต่ละแถวเป็นคนละประเภทหลักฐาน ไม่บวกเป็นคะแนนรวม และไม่เปลี่ยนวันที่ผลเดิมเป็นวันที่นำเสนอ

แนวพูด: “ระบบทดสอบทั้งกฎธุรกิจ API และสถานะหน้าจอ โดยผลชุดที่บันทึกผ่านตามจำนวนในตาราง นอกจากนี้ยังตรวจ flow งานซ่อมจนผู้พักปิดงาน และย้ายออกแล้วลบข้อมูลกับไฟล์ที่ผูกผู้พัก โดยเก็บบัญชีให้สมัครใหม่ได้ ผลเหล่านี้ยืนยันเฉพาะกรณีที่ตรวจ ส่วนอุปกรณ์และบริการภายนอกจริงยังเป็นขอบเขตทดสอบแยกครับ”

**หน้า 13 — จุดเด่นและข้อจำกัดของระบบ**

หน้านี้ตอบว่า “ระบบช่วยแก้ปัญหาอย่างไร และยังติดข้อจำกัดอะไร” จัดด้านซ้ายเป็นตารางจุดเด่นสามแถว ด้านขวาเป็นข้อจำกัดสองข้อ ลบหัวข้อ SYSTEM TESTING และผลการพัฒนาเดิมที่ซ้ำกับหน้า 12 ออก

| ปัญหาเมื่อจัดการข้อมูลแยกส่วน | สิ่งที่ระบบนี้รองรับ |
|---|---|
| ต้องกรอกข้อมูลเดิมในหลายขั้นตอน | ตรวจแก้ข้อมูลจาก OCR แล้วใช้ต่อถึงสัญญา |
| ทำรายการสะดุดและไม่แน่ใจยอดที่จ่ายแล้ว | กู้ฉบับร่างและเครดิตที่ตรวจผ่านจาก server แล้วคำนวณส่วนขาดเมื่อเปลี่ยนห้อง |
| สถานะงานและข้อมูลหลังย้ายออกติดตามแยกกัน | งานซ่อมจบด้วยผู้พักยืนยันปิดงาน และมี flow ย้ายออก/ตรวจการล้างข้อมูลที่ผูกผู้พัก |

ข้อจำกัดที่ใส่บนสไลด์:

- **พึ่งพาบริการภายนอก:** OCR/Face/Payment ขัดข้องอาจทำให้บางขั้นตอนต้องรอหรือลองใหม่ และข้อมูล OCR ต้องให้ผู้ใช้ตรวจแก้
- **สถานะอ่านแจ้งเตือนยังแยกตามเบราว์เซอร์:** ยังไม่ซิงก์สถานะอ่านข้ามเครื่อง

กำกับสั้น ๆ ว่า “ยังไม่มีผลประเมิน accuracy ใบหน้า หรือสมรรถนะใช้งานจริงระยะยาว; ประตู/อุปกรณ์จริงอยู่นอกขอบเขต QA” ข้อความนี้เป็นข้อจำกัดของหลักฐาน แยกจากปัญหาการใช้งานสองข้อด้านบน

แนวพูด: “จุดเด่นของระบบคือเชื่อมข้อมูลและสถานะตลอดขั้นตอน ผู้สมัครตรวจข้อมูลครั้งแรกแล้วใช้ต่อถึงสัญญาได้ หากรีเฟรชก็กลับมาทำต่อพร้อมตรวจเครดิตเดิม งานซ่อมและการย้ายออกมีปลายทางที่ตรวจสอบได้ เมื่อเทียบกับการใช้แบบฟอร์มหรือไฟล์แยกกันจึงช่วยให้ทำรายการต่อเนื่องขึ้น ข้อจำกัดคือยังพึ่งบริการภายนอก และสถานะอ่านแจ้งเตือนยังไม่ซิงก์ข้ามเครื่องครับ”

กรอบเปรียบเทียบนี้ใช้ “การจัดการข้อมูลด้วยแบบฟอร์มหรือไฟล์แยกกัน” เป็นกรณีอธิบายประโยชน์ ไม่ใช่ผลทดลองเปรียบเทียบผลิตภัณฑ์ ห้ามเปลี่ยนเป็น “ดีกว่าเว็บทั่วไปทุกระบบ” หรืออ้างว่าเร็วกว่า/แม่นยำกว่ากี่เปอร์เซ็นต์โดยไม่มีข้อมูลเปรียบเทียบ หากต้องการเปรียบเทียบเว็บจริง ต้องระบุระบบ รุ่น เกณฑ์ และหลักฐานเพิ่ม

**หน้า 14 — สรุปผลตามวัตถุประสงค์**

หน้านี้ตอบว่า “พัฒนาได้อะไรตามที่ตั้งใจ” ไม่ทำตารางจุดเด่น/จุดด้อยซ้ำกับหน้า 13 ใช้สามประเด็นหลัก:

1. **พัฒนาเว็บบริหารหอพัก:** ครอบคลุมสมัครและสัญญา ห้อง/ผู้พัก บิล งานซ่อม และผู้มาติดต่อ
2. **เชื่อมข้อมูลและสถานะ:** ผู้พักทำรายการของตนเอง ผู้ดูแลตรวจและจัดการผ่านสิทธิ์ที่กำหนด โดยเก็บข้อมูลหลักในฐานข้อมูลร่วมกัน
3. **เชื่อมบริการช่วยประมวลผล:** ใช้ OCR ช่วยกรอกข้อมูล และเชื่อมบริการตรวจใบหน้า/ชำระเงิน โดยตรวจผลและจัดการข้อผิดพลาดในระบบ

ด้านล่างแยกกรอบเล็ก “งานต่อยอด” จากผลที่ทำแล้ว: “ประเมินกับผู้ใช้และโหลดระยะยาว พร้อมทดสอบ provider/อุปกรณ์จริงเมื่อขยายขอบเขต” อย่าเขียนเหมือนงานเหล่านี้ผ่านแล้ว และอย่าสรุปว่าระบบลดเวลาเป็นตัวเลขหรือมีความแม่นยำสูงโดยไม่มีผลวัด

แนวพูด: “สรุปโครงงานนี้ได้พัฒนาเว็บบริหารหอพักที่เชื่อมข้อมูลตั้งแต่สมัครถึงย้ายออก ผู้พักและผู้ดูแลทำงานตามสิทธิ์ พร้อมเชื่อมบริการ OCR ใบหน้า และการชำระเงิน ผลที่บันทึกยืนยันการทำงานตามกรณีทดสอบ ส่วนงานต่อไปคือประเมินกับผู้ใช้และทดสอบสภาพใช้งานจริงเพิ่มเติม ขอบคุณครับ”

หน้าสรุปต้องอ่านร่วมกับวัตถุประสงค์หน้า 3 โดย OCR และ Face เป็นการเชื่อมบริการภายนอก ไม่ใช่ข้ออ้างว่าพัฒนา engine เองหรือรับรองการเปิดประตูจริงแล้ว
