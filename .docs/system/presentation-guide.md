# แนวทางนำเสนอสอบโครงงาน MEEDEE Dormitory

จัดทำ 14 ตุลาคม 2569 จากข้อกำหนดสอบที่ผู้ใช้ให้และหลักฐานในเอกสารระบบ ใช้เป็นโครงทำสไลด์และซ้อมพูด ยังไม่ใช่ไฟล์ PowerPoint และยังไม่มีภาพหน้าจอแนบ

## 1. สิ่งที่ต้องเตรียมตามข้อกำหนดสอบ

| เรื่อง | สิ่งที่ต้องทำ |
|---|---|
| เวลาไปถึง | ถึงก่อนเวลาสอบอย่างน้อย 10 นาที; เผื่อเวลาต่อเครื่องและเปิดไฟล์ด้วย |
| กลุ่มที่มีบางคนหรือทั้งกลุ่มไปสหกิจ | เตรียมรายงานบทที่ 1–5 |
| กลุ่มที่ทำโปรเจกต์ 2 ต่อทั้งกลุ่ม | เตรียมรายงานบทที่ 1–4 รวมผลทดลองบางส่วน |
| รายงานกรรมการ | เตรียม 4 ฉบับ เนื้อหาและรุ่นเอกสารตรงกัน |
| นำเสนอ | 10 นาที เรียงบทที่ 1 → 2 → 3 → 4 → 5 |
| ตอบคำถาม | 10 นาที เตรียมหลักฐานสำหรับเปิดตอบเพิ่มเติม |
| วิธีพูด | อธิบายจากภาพและประเด็นสำคัญ ไม่อ่านย่อหน้าบนสไลด์ |

เลือกชุดรายงานตามสถานะจริงของกลุ่ม ไม่สรุปจากการที่มีไฟล์ครบ 5 บทแล้ว หากกลุ่มส่งบท 1–4 ให้ใช้ช่วงท้ายเสนอข้อสรุปผลที่มีและแผนงานต่อ แทนการอ้างว่าบท 5 ผ่านข้อกำหนดแล้ว โดยตรวจรูปแบบกับอาจารย์ผู้รับผิดชอบก่อนพิมพ์

## 2. เรื่องหลักที่กรรมการควรเข้าใจ

ระบบเชื่อมการสมัครเข้าพัก ห้อง สัญญา การชำระเงิน งานซ่อม และผู้มาติดต่อเข้าด้วยกัน ผู้พักทำรายการของตนเอง ผู้ดูแลจัดการและตรวจสถานะ ส่วนข้อมูลกับสถานะสำคัญอยู่ในฐานข้อมูล ทำให้ติดตามงานต่อและตรวจการล้างข้อมูลได้

เลือกย้ำผลงาน 3 ประเด็น:

1. สมัคร 4 ขั้น ใช้ข้อมูลเดิมต่อถึงสัญญา และกู้ฉบับร่างกับยอดชำระหลังรีเฟรชได้
2. งานมีปลายทางชัดเจน เช่น ผู้พักยืนยันปิดงานซ่อม และผู้ดูแลตรวจสถานะรวม
3. ควบคุมสิทธิ์ ความยินยอม และการลบข้อมูลที่ผูกผู้พัก โดยบัญชียังสมัครใหม่ได้

ใช้ปัญหาจากการพัฒนาและตรวจระบบเป็นตัวอย่าง ไม่อ้างว่ามีผลสำรวจหอพักหรือการสัมภาษณ์ผู้ใช้ หากยังไม่มีหลักฐานนั้น

## 4. เนื้อหาและแนวพูดรายสไลด์

### หน้า 1 — ชื่อโครงงานและปัญหา

**บนสไลด์:** ชื่อระบบ ผู้จัดทำ และภาพเดียวที่สื่อว่าข้อมูลสมัคร ห้อง บิล และงานซ่อมต้องเชื่อมกัน ข้อความปัญหาไม่เกิน 3 ข้อ

**แนวพูด:** “โครงงานนี้พัฒนาระบบบริหารจัดการหอพัก MEEDEE Dormitory ให้ผู้พักและผู้ดูแลทำงานบนข้อมูลชุดเดียวกัน ประเด็นที่แก้คือการกรอกข้อมูลซ้ำ สถานะงานไม่ต่อเนื่อง และข้อมูลที่ยังค้างหลังลบผู้พัก วันนี้จะนำเสนอแนวคิด การออกแบบ และผลทดสอบตามลำดับบทครับ/ค่ะ”

ที่มา: [บทที่ 1](01-introduction.md)

### หน้า 2 — วัตถุประสงค์และขอบเขต

**บนสไลด์:** ผู้ดูแล / ผู้พัก / ผู้มาติดต่อ พร้อมหน้าที่หลักคนละ 1 บรรทัด และวัตถุประสงค์ 3 ข้อ ได้แก่ รวมงานหอพัก ลดการกรอกซ้ำ และติดตามสถานะ/ตรวจข้อมูลได้

**แนวพูด:** “ผู้พักสมัคร ชำระบิลและแจ้งซ่อม ผู้ดูแลจัดห้อง ตรวจใบสมัครและติดตามงาน ส่วนผู้มาติดต่อส่งคำขอเข้าพบ ขอบเขตที่ตรวจในรอบนี้คือเว็บ API ฐานข้อมูลและไฟล์ ส่วนกล้อง ประตู SMS และบริการภายนอกจริงยังไม่ใช้เป็นผลรับรองของรอบทดสอบนี้”

ใส่ขอบเขตที่ยังไม่ตรวจเป็นแถบสั้น ๆ ไม่ใช้พื้นที่ครึ่งสไลด์ และไม่กล่าวว่าถอดการเชื่อมต่อเหล่านั้นออกจากระบบแล้ว

### หน้า 3 — แนวคิดและเทคโนโลยี

**บนสไลด์:** ตารางสั้นหรือภาพ 4 กลุ่ม: พัฒนาเว็บด้วย TypeScript/React/Express, เก็บข้อมูลด้วย PostgreSQL/Prisma, งานชั่วคราวด้วย Redis, จัดบริการด้วย Docker Compose

**แนวพูด:** “เลือกจัดโครงสร้างตามงาน เช่น ผู้พัก บิล และซ่อม เพื่อดูแลกฎแต่ละส่วนได้ชัดเจน PostgreSQL เก็บข้อมูลหลัก Redis ใช้ cache และล็อกชั่วคราว ส่วน OCR และใบหน้าเรียกผ่านบริการที่เชื่อมต่อ ไม่ได้สร้าง engine ขึ้นใหม่ในโครงงานนี้”

ไม่ไล่รายชื่อทุก package แยกประเภทให้ถูก: TypeScript เป็นภาษา React เป็น UI library Express เป็น web framework และ Vite เป็นเครื่องมือพัฒนา/build

ที่มา: [บทที่ 2](02-background-and-methods.md), [เทคโนโลยีหลัก](deployment-and-data.md)

### หน้า 4 — ออกแบบภาพรวมและข้อมูล

**บนสไลด์:** แผนภาพระบบเดียว แสดงผู้ใช้งาน → เว็บ/API → ฐานข้อมูล/ไฟล์ และความสัมพันธ์ User → Tenant → Room, Bill และ MaintenanceTicket

**แนวพูด:** “เราแยกบัญชี User ออกจากข้อมูลการเข้าพัก Tenant บัญชีจึงยังอยู่เมื่อย้ายออกและลบโปรไฟล์ ห้อง บิล และงานซ่อมเชื่อมกับการเข้าพัก ทำให้ตรวจสิทธิ์และติดตามข้อมูลที่ต้องลบได้”

ใช้เฉพาะข้อมูลหลักในภาพ ไม่ใส่ทุกตารางใน ER บนสไลด์เดียว เก็บ ER ละเอียดเป็นสไลด์สำรอง และไม่วาดตาราง Building/Course ที่ไม่มีใน schema จริง

ที่มา: [บทที่ 3](03-system-design.md)

### หน้า 5 — ออกแบบ flow

**บนสไลด์:** รับทราบ/ยินยอมข้อมูลสมัคร → สมัคร 4 ขั้น → ผู้ดูแลอนุมัติ → ใช้งานระหว่างพัก → ย้ายออก/ลบข้อมูล ส่วนบันทึกใบหน้ามีจุดยินยอมแยก

**แนวพูด:** “ก่อนเริ่มสมัครมีคำชี้แจงข้อมูลส่วนบุคคล จากนั้นตรวจตัวตนและข้อมูลส่วนตัว กรอกผู้ติดต่อ เลือกห้องและชำระเงิน แล้วตรวจสัญญาก่อนยื่น ข้อมูลตัวตนส่งต่อถึงสัญญา ไม่ต้องกรอกใหม่ การตรวจชำระกับการอนุมัติเข้าพักเป็นคนละสถานะ”

จุดยินยอมอยู่ก่อน flow ไม่เรียกเป็นขั้นที่ 5 ของใบสมัคร และไม่รวมการยินยอมใบหน้ากับการยอมรับสัญญา

ที่มา: [ผู้พักและสัญญา](users-and-tenants.md), [การชำระเงิน](billing-and-payments.md)

### หน้า 6 — ผลพัฒนาการสมัครและการกู้ข้อมูล

**บนสไลด์:** ภาพหน้าสมัครที่ตรวจแก้ข้อมูล กับภาพสัญญาหรือยอดชำระเดิม ใช้เลขกำกับว่า “กรอกครั้งแรก → นำไปใช้ต่อ → รีเฟรชทำต่อได้”

**แนวพูด:** “ข้อมูลที่อ่านจากบัตรให้ผู้สมัครตรวจแก้ก่อนนำไปใช้ในสัญญา ระบบเก็บฉบับร่างและเครดิตที่ตรวจผ่านไว้กับบัญชี เมื่อรีเฟรชจึงกลับมาทำต่อได้ การเปลี่ยนห้องคำนวณยอดขาดจากยอดเดิม และยังต้องผ่านกฎการตรวจชำระ ไม่ถือว่าสร้าง QR แล้วแปลว่าจ่ายสำเร็จ”

ใช้ภาพข้อมูลทดสอบ ปิดข้อมูลบัตรและสลิปจริง ไม่โอนเงินสดหรือเริ่มสมัครใหม่ทั้ง flow ระหว่างนำเสนอ 10 นาที หากใช้คลิปสาธิตสั้นให้รวมไว้ใน 75 วินาทีของหน้านี้

### หน้า 7 — ผลพัฒนางานผู้ดูแลและงานซ่อม

**บนสไลด์:** ภาพ Dashboard ที่อ่านตัวเลขได้ และเส้นสถานะงานซ่อม PENDING → APPROVED → IN_PROGRESS → RESOLVED → CLOSED

**แนวพูด:** “ผู้ดูแลเห็นภาพรวมห้อง บิลและกิจกรรมล่าสุด งานซ่อมแยกซ่อมเสร็จออกจากปิดงาน ผู้พักเป็นผู้ยืนยันขั้นสุดท้าย ผลที่ตรวจจริงมีงานทดสอบที่ผู้พักยืนยัน CLOSED แล้ว ส่วนการแจ้งเตือนแยกตามสิทธิ์และบัญชี”

ผู้มาติดต่อให้กล่าวเพิ่มเพียง 1 ประโยคว่า “ผู้มาติดต่อส่งคำขอและดาวน์โหลดหลักฐาน PNG ได้ ส่วนการเข้าพบและข้อมูลของคนอื่นถูกจำกัดสิทธิ์” เก็บภาพและ flow ละเอียดไว้ตอบคำถาม

ที่มา: [งานซ่อม](maintenance.md), [Dashboard/รายงาน](reports-and-audit.md), [ผู้มาติดต่อ](visitors.md)

### หน้า 8 — ข้อมูลส่วนบุคคลและการล้างข้อมูล

**บนสไลด์:** ความยินยอม 2 กล่อง HOUSING / FACE_ENROLLMENT และตารางสั้น “ข้อมูล/ไฟล์ผู้พักถูกล้าง — บัญชี User ยังอยู่”

**แนวพูด:** “ใบสมัครและใบหน้าใช้ความยินยอมคนละวัตถุประสงค์ บันทึกบัญชี รุ่นข้อความ และเวลาไว้ในฐานข้อมูล ก่อนเก็บภาพระบบตรวจหลักฐานอีกครั้ง ส่วนการลบผู้พักตรวจทั้งฐานข้อมูล ไฟล์และคิวล้าง ผลทดสอบเดิมล้างไฟล์ 10 รายการและคิว 11 งานสำเร็จ โดยบัญชียังสมัครใหม่ได้”

แยกผลให้ชัด: การลบเป็น runtime ที่ตรวจไว้ก่อนหน้า ส่วนหน้าความยินยอมใหม่ผ่าน automated tests และ smoke แต่ยังรอการตรวจผ่านหน้าจอจริง ไม่อ้างว่าลบภาพใบหน้าจริงผ่านแล้ว เพราะบัญชีทดสอบรอบนั้นไม่มีภาพใบหน้า และไม่อ้างว่าเพิ่ม checkbox แล้วผ่าน PDPA ครบทุกด้าน

ที่มา: [ผู้พักและการลบ](users-and-tenants.md), [ใบหน้า](face-verification.md)

### หน้า 9 — ผลทดสอบ

**บนสไลด์:** ตาราง 3 แถวต่อไปนี้ พร้อมวันที่และชนิดหลักฐาน

| ชุดหลักฐาน | ผลที่ใช้บนสไลด์ | ความหมาย |
|---|---|---|
| กฎธุรกิจ/API unit และ mock วันที่ 14 ต.ค. 2569 | 185/185 ผ่าน | กรณีที่กำหนดใน suite ไม่ใช่ทุก flow ผ่านหน้าจอ |
| Logic/สถานะหน้าจอ unit/VM วันที่ 14 ต.ค. 2569 | 119/119 ผ่าน | รวมความยินยอม กดซ้ำ รีเฟรชและยกเลิกคำขอ |
| Runtime ที่บันทึกก่อนหน้า | ชำระบิล → ปิดงานซ่อม → ย้ายออก/ลบ → สมัครใหม่ | API/DB/files และการยืนยันผู้ใช้ตามรายการในรายงาน |

**แนวพูด:** “ทดสอบทั้งกฎธุรกิจ การตรวจสิทธิ์ และการจัดการสถานะหน้าจอ รวมถึง flow ที่ตรวจ API ฐานข้อมูลและไฟล์ ผล suite ล่าสุดผ่านตามจำนวนนี้ แต่ไม่ได้ใช้แทนผลอุปกรณ์หรือ provider จริง สิ่งที่เน้นตรวจเป็นพิเศษคือการกรอกซ้ำ การส่งซ้ำ และข้อมูลตกค้างหลังลบ”

หากแสดงร้อยละ ให้ระบุว่าเป็นสัดส่วนกรณีทดสอบในชุดที่ผ่าน ไม่เรียกว่า accuracy หรือความปลอดภัย 100% ชุด integration 38/38, 27/27 และ 29/29 เป็นคนละรอบ เก็บในภาคสำรอง ไม่บวกเป็นการรันครั้งเดียว

ที่มา: [บทที่ 4 และชนิดหลักฐาน](04-implementation-and-results.md)

### หน้า 10 — สรุปและงานต่อยอด

**บนสไลด์:** ผลสำเร็จ 3 ข้อ ข้อจำกัด 1 กลุ่ม และงานถัดไป 2 ข้อ

**แนวพูด:** “ผลที่ได้คือระบบรวมงานหอพัก ใช้ข้อมูลต่อเนื่อง และตรวจสถานะกับการล้างข้อมูลได้ตามกรณีที่ทดสอบ ข้อจำกัดคือยังไม่มีผลรับรองอุปกรณ์และบริการจริงครบทุกส่วน งานต่อไปคือทดสอบส่วนเชื่อมต่อในสภาพใช้งานจริงและเพิ่มหลักฐานการใช้งานกับการกู้คืนข้อมูล ขอบคุณครับ/ค่ะ”

ไม่กล่าวว่าลดเวลางานได้กี่เปอร์เซ็นต์ ผู้ใช้พึงพอใจเท่าใด หรือรองรับ production แล้ว หากยังไม่ได้วัด

## 5. ภาพและสไลด์สำรอง

สไลด์หลักเลือกภาพที่อ่านข้อความได้ ไม่ย่อหน้าจอทั้งระบบจนตัวหนังสือเล็ก ภาพประกอบต่อไปนี้ยังต้องจับจากระบบจริงโดยใช้ข้อมูลทดสอบ

| ใช้ในหน้าหลัก | ภาพที่ควรเตรียม |
|---|---|
| หน้า 4–5 | แผนภาพภาพรวม/ข้อมูล และ flow สมัคร 4 ขั้น |
| หน้า 6 | ข้อมูลส่วนตัวที่ตรวจแก้ สัญญา และฉบับร่าง/ยอดเดิม |
| หน้า 7 | Dashboard และงานซ่อมที่สถานะปิดแล้ว |
| หน้า 8 | คำชี้แจงข้อมูลสมัคร/ใบหน้า และผลตรวจ cleanup แบบไม่แสดงข้อมูลบุคคล |
| หน้า 9 | ตารางผลทดสอบสรุป ไม่ใช้ terminal หลายร้อยบรรทัด |

เตรียมสไลด์สำรองสำหรับถามตอบ: ER ละเอียด, ตัวอย่างบิลแยกประเภท, ผู้มาติดต่อ/หลักฐาน PNG, ตารางทดสอบสิทธิ์, รายละเอียด cleanup, และผล load พร้อมเงื่อนไข สไลด์สำรองไม่ต้องเปิดไล่ในช่วงนำเสนอ 10 นาที

## 6. คำถามที่ควรเตรียมตอบใน 10 นาที

ตอบข้อสรุปก่อน แล้วอธิบายกฎและชี้หลักฐานสั้น ๆ ถ้าไม่ได้ทดสอบให้ระบุขอบเขตนั้น แทนการคาดเดา

| คำถาม | แนวตอบจากระบบปัจจุบัน |
|---|---|
| จุดเด่นคืออะไร ต่างจากฟอร์มทั่วไปอย่างไร | ข้อมูลและสถานะเชื่อมกันตั้งแต่สมัครถึงย้ายออก มี draft/เครดิต กฎสิทธิ์ และตรวจการล้างข้อมูล ใช้ flow ที่ทดสอบเป็นตัวอย่าง ไม่อ้างความใหม่เชิงวิจัยโดยไม่มีงานเปรียบเทียบ |
| รีเฟรชหลังจ่ายต้องจ่ายอีกไหม | Draft และรายการชำระผูกบัญชีในฐานข้อมูล ระบบตรวจเครดิตเดิมก่อนคำนวณยอดคงเหลือ ไม่ใช้สถานะหน้าจอหรือ QR เป็นหลักฐานว่าโอนแล้ว |
| เปลี่ยนห้องหลังชำระได้อย่างไร | ใช้เครดิตที่ตรวจผ่านคำนวณยอดขาดตามห้องใหม่ ภายใต้ guard รายการรอตรวจ/ความจุ ยอดเกินไม่ใช่การคืนเงินธนาคารอัตโนมัติ |
| ใครตรวจว่าโอนจริง | ผ่าน integration ตรวจชำระและข้อมูลธุรกรรม แยกการตรวจสลิปจากการอนุมัติเข้าพักและการนับมัดจำ รอบทดสอบใช้ provider mock ตามที่รายงาน ไม่อ้างว่าทุกธนาคารผ่าน |
| ป้องกันคนอื่นอ่านบิล/งานซ่อมอย่างไร | ตรวจ session, role และเจ้าของข้อมูลใน API/บริการ รวม Socket ไม่ใช้เพียงการซ่อนปุ่ม |
| ลบผู้พักแล้วเหลืออะไร | User คงอยู่ ข้อมูลและไฟล์ที่ผูกผู้พักถูก purge หลังผ่าน guard พร้อมคิว cleanup ตรวจจนเสร็จ ห้องคืนว่าง และสมัครใหม่ได้ |
| ลบข้อมูลการเงินด้วยหรือ | นโยบายปัจจุบันลบรายการที่ผูกผู้พักทั้งหมดตามขอบเขตโครงงาน จึงไม่อ้างว่าเป็นระบบบัญชีถาวร การนำไปใช้จริงต้องทบทวนนโยบายเก็บข้อมูล |
| ทำไมเก็บภาพเป็นไฟล์ | ฐานข้อมูลเก็บ reference/ข้อมูลสัมพันธ์ ต้องสำรองฐานข้อมูลและไฟล์ร่วมกัน และตรวจการลบทั้งสองส่วน ไม่ได้สรุปว่าไฟล์ไม่มีความเสี่ยง |
| ใบหน้าแม่นยำเท่าใด พัฒนาโมเดลเองไหม | ระบบเชื่อมบริการภายนอก ไม่สร้าง engine ใหม่ ยังไม่มีชุดประเมิน accuracy จึงไม่แปลง similarity เป็นเปอร์เซ็นต์ความแม่นยำ |
| มี PDPA แล้วถือว่าครบหรือไม่ | แยกคำชี้แจง/ความยินยอมตามวัตถุประสงค์และเก็บหลักฐานแล้ว ยังต้องพิจารณาฐานกฎหมาย ผู้ประมวลผล ระยะเวลาเก็บและการใช้สิทธิ์ตามการใช้งานจริง การถอนในระบบรอบนี้ติดต่อผู้ดูแล |
| หมดสัญญาแล้วรูปใบหน้าหายเองไหม | ยังไม่ล้างอัตโนมัติจากวันหมดสัญญาเพียงอย่างเดียว ต้องใช้ flow ย้ายออก/ลบ/cleanup ที่กำหนด |
| ข้อมูลเปลี่ยนแบบ real-time จริงหรือ | มี Socket.IO และบางหน้ามี refresh สำรอง 30 วินาที ไม่ใช่ทุกหน้าหรือทุกเหตุการณ์ใช้วิธีเดียวกัน |
| รองรับได้กี่คน หรือ RPS/TPS เท่าใด | ผล bounded local ล่าสุดที่อ้างไว้คือ 12 คำขอ concurrency 4 ประมาณ 77.67 RPS/TPS ภายใต้เงื่อนไขรายงาน ไม่ใช่ sustained capacity และแปลงเป็นจำนวนผู้ใช้จริงไม่ได้โดยตรง |
| ทดสอบครบทุก endpoint แล้วหรือ | มี source review, unit/mock, integration และ runtime เป็นรายการ ผลจำนวน tests ไม่ยืนยันทุก browser flow กล้อง/ประตู/SMS/provider จริงอยู่นอกขอบเขตรอบนี้ |

## 7. วิธีซ้อมและแบ่งการพูด

1. รอบแรกเล่าจากหัวข้อให้เข้าใจ ก่อนปรับให้ตรงเวลา อัดเสียงฟังว่ามีคำเทคนิคที่ไม่อธิบายหรือไม่
2. รอบที่สองจับเวลาตามตาราง ต้องเข้าเนื้อหาผลพัฒนาภายในนาที 4:35 หากช้าให้ตัดรายละเอียด package และรายชื่อหน้าจอ
3. รอบสุดท้ายใช้เครื่องและไฟล์ที่จะนำไปสอบ เป้าซ้อมประมาณ 9:30–9:45 เพื่อเผื่อจังหวะเปลี่ยนหน้า โดยเวลาสูงสุดยังเป็น 10 นาที
4. หากนำเสนอหลายคน ให้แบ่งช่วงตามบทและส่งต่อประโยคเดียว ตกลงล่วงหน้าว่าใครรับคำถามเรื่องข้อมูล สิทธิ์ และการทดสอบ ไม่กำหนดจำนวนผู้พูดจนกว่าจะทราบสมาชิกจริง
5. ให้เพื่อนถามจากตารางข้อ 6 ตอบประมาณ 30–45 วินาทีต่อคำถาม และเปิดสไลด์สำรองเฉพาะเมื่อช่วยยืนยันคำตอบ

โพยผู้พูดต่อหน้าใช้เพียง “ประเด็นหลัก → ตัวอย่าง → ผล” ไม่คัดแนวพูดทั้งหมดไปใส่ในสไลด์ ขณะพูดให้อธิบายว่าภาพแสดงอะไรและแก้ปัญหาอย่างไร

## 8. ตรวจความพร้อมก่อนวันสอบ

- เลือกรายงาน 1–5 หรือ 1–4 ให้ตรงกลุ่ม และเตรียม 4 ฉบับ
- เติมข้อมูลผู้จัดทำ อาจารย์ สถานศึกษา รูปจริง และบรรณานุกรมตามรูปแบบที่กำหนด ตรวจเลขหน้า/สารบัญก่อนพิมพ์
- ตรวจว่ารายงานกับสไลด์ใช้ผล 185/119 พร้อมชนิดหลักฐานและวันที่ตรงกัน ไม่เปลี่ยนวันที่ผลทดลองเก่าเป็นวันสอบ
- ส่งออกสไลด์เป็น PDF สำรอง พร้อมไฟล์ต้นฉบับ และทดสอบเปิดแบบออฟไลน์
- ปกปิดเลขบัตร เบอร์โทร สลิป token และใบหน้าจริงในทุกภาพ
- หากเตรียมสาธิต ให้ใช้บัญชี/ข้อมูลทดสอบ ตรวจสถานะก่อนสอบ และมีภาพหรือคลิปสำรอง ไม่เริ่มโอนเงินจริงหรือ purge ข้อมูลใช้งานจริงต่อหน้ากรรมการ
- ตรวจจอ ฟอนต์ สายต่อและเครื่องให้พร้อม และมาถึงก่อนเวลาอย่างน้อย 10 นาที
