# บทที่ 4 การพัฒนาและผลการทดสอบ

บทนี้สรุปผลจากระบบต้นแบบและหลักฐานที่บันทึกถึง 19 ตุลาคม 2569 โดยแยกผลชุดทดสอบอัตโนมัติ การเชื่อมต่อฐานข้อมูล การตรวจ runtime และการทดลองผ่านหน้าจอออกจากกัน วันที่ของแต่ละผลระบุแยกไว้ เพราะไม่ได้รันทุกรายการพร้อมกันในรอบเดียว

## 4.1 วิธีจัดผลและสภาพแวดล้อม

ใช้ local Docker/API gateway สำหรับ runtime และฐานข้อมูลทดสอบที่แยกจากฐานใช้งานจริงสำหรับ integration ผลแบ่งเป็น source review (SR), unit/mock (UT), HTTP/DB integration (IT), runtime HTTP/DB/files (RT), user acceptance (UA) และ out of scope (OS)

การที่ผู้ใช้รายงานว่าใช้งานปกติบันทึกเป็น UA และไม่ใช้แทนหลักฐานรายละเอียดที่ไม่มี การทดสอบ provider ด้วย Mock ยืนยันเฉพาะพฤติกรรมที่จำลองไว้ ไม่ยืนยันคุณภาพบริการจริง ระบบสมัครมี 4 ขั้น และการ purge ลบข้อมูล/ไฟล์ที่ผูกกับผู้พักตาม guard ที่กำหนด โดยเก็บบัญชี User ไว้

## 4.2 ผลการพัฒนาระบบบัญชีและสิทธิ์

ระบบแยกบัญชี User ออกจากข้อมูลผู้พัก Tenant ผู้ใช้สมัครบัญชีและเข้าสู่ระบบด้วยอีเมลกับรหัสผ่าน Backend ตรวจข้อมูลและสิทธิ์ทุกคำขอ โดย session ส่งผ่าน HttpOnly cookie และตรวจรุ่น session กับบัญชีใน PostgreSQL การเข้าสู่ระบบใหม่ทำให้ session เก่าหมดสิทธิ์ตามกติกาปัจจุบัน ส่วนการกู้รหัสผ่านใช้ OTP ตาม flow ที่พัฒนา โดยการส่ง OTP ภายนอกจำลองในการทดสอบ จึงไม่ถือเป็นผลทดสอบ SMS provider จริง

Admin จัดการบัญชีและข้อมูลตาม role; ผู้ใช้ทั่วไปอ่านหรือแก้ไขข้อมูลที่ผูกกับบัญชีของตนเอง การตรวจสิทธิ์ไม่พึ่ง userId ที่ส่งจากหน้าจอเพียงอย่างเดียว ในกรณีถูกปฏิเสธใบสมัคร ระบบคืนสถานะให้บัญชีกลับเข้าสู่ flow สมัครใหม่ได้ โดยไม่สร้างปุ่มคืนสถานะพิเศษสำหรับผู้สมัคร

**ตำแหน่งภาพ 4.1 (หน้าเข้าสู่ระบบ):** ให้จับหน้า Login ที่ไม่มีข้อมูลจริงกรอก หรือใช้บัญชีทดสอบที่ปกปิดอีเมล/รหัสผ่าน แสดงเฉพาะหน้าจอระบบ ไม่แสดง DevTools หรือ cookie
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.1 หน้าเข้าสู่ระบบ

## 4.3 ผลการพัฒนาการสมัครและจัดการผู้พัก

แบบสมัครแบ่งเป็น 4 ขั้น ได้แก่ (1) ยืนยันตัวตนและข้อมูลส่วนตัว (2) ผู้ติดต่อฉุกเฉิน (3) เลือกห้องและชำระเงิน และ (4) ตรวจสัญญาและส่งใบสมัคร ระบบเก็บข้อมูลเป็น draft ใน PostgreSQL เพื่อให้กลับมาทำต่อหลังรีเฟรชได้ ก่อนส่งข้อมูลสำคัญ Backend ตรวจซ้ำและบันทึก snapshot สัญญาไว้กับรายการที่ส่งแล้ว

ผู้สมัครต้องยินยอมวัตถุประสงค์ HOUSING ก่อนกรอกแบบฟอร์มหรือส่งเอกสาร ความยินยอมนี้แยกจากการยอมรับสัญญา วันเริ่มสัญญาใหม่คำนวณจากวันปัจจุบันตามเวลา Asia/Bangkok และวันสิ้นสุดบวก 5 เดือนปฏิทิน โดยปรับเป็นวันสุดท้ายของเดือนเมื่อไม่มีวันที่ตรงกัน เงื่อนไขส่วนกลางในสัญญากำหนดโดย Admin; หากวันเปลี่ยนก่อนยืนยัน ระบบโหลดเงื่อนไขล่าสุดก่อนส่ง

Admin พิจารณาใบสมัครและเปลี่ยนสถานะผู้พัก การชำระเงินผ่านไม่ได้ทำให้ใบสมัครอนุมัติอัตโนมัติ เมื่อย้ายออก ระบบตรวจบิลและงานค้างก่อนคืนห้อง การลบข้อมูลผู้พักใช้ guarded purge ลบข้อมูลสัมพันธ์และไฟล์ แต่เก็บบัญชี User ไว้ให้สมัครใหม่ได้ การลบไฟล์ดำเนินผ่าน cleanup job และต้องรอผลเสร็จ ไม่สรุปว่าเสร็จจากการลบแถว Tenant อย่างเดียว

**ตำแหน่งภาพ 4.2 (แบบสมัครขั้นข้อมูลส่วนตัว):** จับหน้าที่เห็นแถบขั้นตอนและแบบฟอร์มโดยใช้ข้อมูลตัวอย่าง ไม่ใช้ชื่อ เลขบัตร ที่อยู่ หรือเบอร์โทรจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.2 แบบสมัครขั้นข้อมูลส่วนตัว
**ตำแหน่งภาพ 4.3 (ขั้นเลือกห้องและสรุปค่าใช้จ่าย):** แสดงห้องที่เลือก ค่าเช่า เงินประกัน ยอดชำระและเครดิต โดยใช้ยอดทดสอบ และปิดบัง QR/ข้อมูลบัญชี
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.3 ขั้นเลือกห้องและสรุปค่าใช้จ่าย
**ตำแหน่งภาพ 4.4 (ตัวอย่างสัญญาก่อนยืนยัน):** ใช้ข้อมูลสมมติทั้งหมดและระบุใต้ภาพว่าเป็นตัวอย่างข้อมูล ไม่ใช่สัญญาจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.4 ตัวอย่างสัญญาก่อนยืนยัน

## 4.4 ผลการจัดการห้องและป้องกันการจองซ้ำ

Admin เพิ่มหรือแก้ไขห้อง กำหนดหมายเลข ชั้น ความจุ สถานะ และค่าเช่ารายเดือน การเลือกห้องในขั้นสมัครตรวจจำนวนผู้พักและใบสมัครที่กำลังถือสิทธิ์อยู่ ก่อนสร้าง QR ระบบล็อกข้อมูลผู้ใช้และห้องแล้วตรวจความจุซ้ำ สิทธิ์กันห้องมีอายุ 10 นาที บันทึกในฐานข้อมูล และการขอ QR ซ้ำไม่ต่อเวลาเดิม เมื่อหมดเวลา ห้องกลับไปนับเป็นห้องว่างสำหรับผู้สมัครรายอื่นโดยไม่ต้องรอ worker

มีการทดสอบ Integration แบบ PostgreSQL แยกในกรณีห้องเหลือหนึ่งห้อง 8/8 กรณี ครอบคลุมคำขอพร้อมกัน การแข่งกับ Admin การหมดอายุ การตรวจยอดค้าง การเปลี่ยนห้อง และการยืนยันว่าผู้สมัครได้ห้องไม่เกินความจุ ใช้ provider จำลอง จึงไม่ยืนยันการจ่ายเงินจริงกับธนาคาร

**ตำแหน่งภาพ 4.5 (หน้าจัดการห้องของ Admin):** แสดงรายการห้อง สถานะและความจุ โดยไม่เปิดเผยชื่อผู้พักจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.5 หน้าจัดการห้องของ Admin
**ตำแหน่งภาพ 4.6 (ห้องที่เลือกและเวลาถือสิทธิ์):** จับจากหน้าสมัครด้วยบัญชีทดสอบ แสดงเวลาหมดอายุหาก UI มีข้อมูลนี้ ห้ามใช้ภาพที่ทำให้เข้าใจว่าเป็นการจองถาวร
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.6 ห้องที่เลือกและเวลาถือสิทธิ์

## 4.5 ผลการพัฒนาบิลและการชำระเงิน

ระบบรองรับการออกบิลที่แยกยอดค่าเช่า ค่าน้ำ ค่าไฟ และค่าปรับ แสดงวันครบกำหนดและสถานะ ผู้พักชำระบิลเดี่ยวหรือหลายบิลตาม flow ที่เปิดใช้ ระบบสร้าง QR รับหลักฐาน ตรวจยอดและรายการซ้ำ แล้วบันทึกสถานะ เช่น PENDING, VERIFYING, PAID หรือ FAILED ตามผลตรวจ การเปลี่ยนสถานะที่สำคัญตรวจสิทธิ์และความสอดคล้องของข้อมูลที่ Backend

การชำระสมัครเข้าพักแยกจากบิลผู้พัก ยอดที่ตรวจผ่านแล้วผูกเป็นเครดิตของเจ้าของ draft เมื่อสิทธิ์ห้องหมดอายุ เครดิตยังคงอยู่ ผู้ใช้เลือกนำไปใช้กับห้องใหม่หรือส่งคำขอคืนเครดิตทั้งหมดได้ หากเครดิตเกินยอดห้อง ระบบเตือนก่อนยืนยันว่าการสมัครต่อโดยไม่ขอคืนจะไม่ทำให้มีการคืนส่วนเกินอัตโนมัติ ส่วนการคืนเงินจริงต้องให้ Admin บันทึกยอดอ้างอิงและหลักฐานหลังดำเนินการภายนอกแล้ว ระบบไม่โอนเงินคืนเอง

คำขอคืนเครดิตจัดการในหน้า **จัดการผู้พักอาศัย** เพื่อให้ Admin เห็นคำขอได้แม้ยังไม่มี Tenant ผู้สมัครส่งคำขอแล้วระบบพักการแก้ไข draft การอัปโหลด การชำระ และการยื่นใบสมัครระหว่างรอพิจารณา Admin ปฏิเสธพร้อมเหตุผลได้ หรือบันทึกการคืนเงินจริงหลังคืนแล้ว การคืนเงินจริงแยกจากคำขอและไม่ลบรายการชำระเดิม

การทดสอบการเปลี่ยนห้องและยอดเครดิตรวมอยู่ใน PostgreSQL integration ชุดแยก 12/12 ตาม QA ล่าสุด ส่วนการคืนเครดิตที่เพิ่ม 19 ต.ค. มี unit/build/typecheck ผ่านและมีกรณี PostgreSQL แยกที่เพิ่มไว้ แต่ยังไม่ได้รัน integration ชุดใหม่กับฐานทดสอบ และยังไม่ได้ยืนยันด้วย Browser Acceptance หรือ deploy migration จึงยังสรุปว่า flow คืนเครดิตใช้งานจริงครบวงจรไม่ได้

**ตำแหน่งภาพ 4.7 (หน้าบิลของผู้พัก):** แสดงองค์ประกอบยอดและสถานะด้วยบัญชีทดสอบ
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.7 หน้าบิลของผู้พัก
**ตำแหน่งภาพ 4.8 (คำเตือนยอดเครดิตส่วนเกิน):** จับ modal ก่อนเลือกดำเนินการต่อหรือกลับไปตรวจสอบ โดยใช้ยอดสมมติ
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.8 คำเตือนยอดเครดิตส่วนเกิน
**ตำแหน่งภาพ 4.9 (คำขอคืนเครดิตและหน้าผู้ดูแล):** จัดภาพหน้าผู้สมัครและหน้าผู้ดูแลเป็นภาพย่อย (ก) และ (ข) ในกรอบภาพเดียว หลังระบบ deploy และทดสอบ Browser Acceptance แล้วเท่านั้น; ขณะนี้ยังไม่มีหลักฐานยืนยันหน้าจอครบ flow
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.9 หน้าคำขอคืนเครดิต (ก) มุมมองผู้สมัคร และ (ข) มุมมองผู้ดูแลระบบ

## 4.6 ผลการพัฒนาระบบแจ้งซ่อม

ผู้พักที่มีสถานะและห้องที่ใช้งานได้ส่งคำขอแจ้งซ่อม ระบุประเภท รายละเอียด เวลาติดต่อ และภาพประกอบตามข้อกำหนด Admin รับงาน มอบหมายและเปลี่ยนสถานะตามลำดับ PENDING → APPROVED → IN_PROGRESS → RESOLVED; จากนั้นผู้พักต้องยืนยันปิดงานจึงเป็น CLOSED ระบบจำกัดการสร้างคำขอไม่เกิน 3 รายการต่อบัญชีต่อวันตามเวลาไทย และตรวจ quota ใน PostgreSQL เพื่อให้ทำงานต่อเนื่องแม้ Redis เริ่มใหม่

การทดสอบ Integration ของ maintenance flow ผ่าน 38/38 กรณีในฐานข้อมูลแยก ครอบคลุมสิทธิ์เจ้าของห้อง การส่งพร้อมกันเกิน quota การเปลี่ยนสถานะ และการปฏิเสธแก้ไขหรือลบงานที่ปิดแล้ว มีกรณี runtime ที่ผู้พักยืนยันปิดงานได้และตรวจสถานะ CLOSED ในฐานข้อมูล ผลนี้ไม่ใช่การประเมินความพึงพอใจของผู้ใช้ทั้งหมด

**ตำแหน่งภาพ 4.10 (แบบฟอร์มแจ้งซ่อม):** ใช้ห้องและข้อมูลทดสอบ
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.10 แบบฟอร์มแจ้งซ่อม
**ตำแหน่งภาพ 4.11 (มุมมอง Admin และผู้พักหลังช่างแก้เสร็จ):** แสดง RESOLVED และคำสั่งยืนยันของผู้พัก หรือ CLOSED หลังยืนยัน โดยไม่แสดงข้อมูลติดต่อจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.11 มุมมอง Admin และผู้พักหลังช่างแก้เสร็จ

## 4.7 ผลการพัฒนาระบบผู้มาติดต่อ

ผู้มาติดต่อกรอกข้อมูลจากหน้าสาธารณะ ส่งภาพเอกสารให้ OCR wrapper และตรวจทานผลก่อนยื่นคำขอ Backend ตรวจความยินยอม ข้อมูลจาก verification ห้อง และ Idempotency-Key แล้วบันทึก Visitor กับ VisitorLog ใน PostgreSQL ก่อนคืนเลขอ้างอิงและไฟล์สรุป PNG ชื่อผู้พักที่ผู้มาติดต่อกรอกเป็นข้อความสำหรับให้ Admin ตรวจ ไม่ใช้จับคู่ Tenant โดยคาดเดา

Admin ตรวจคำขอและบันทึกขั้นเข้าพบแยกจากสถานะคำขอ: WAITING → ADMITTED → COMPLETED ส่วน status ของคำขออาจเป็น REGISTERED, CANCELLED หรือ EXPIRED การบันทึกเข้าพบเป็นงานของเจ้าหน้าที่ในระบบ ไม่ใช่หลักฐานว่าประตูจริงเปิดหรือมีอุปกรณ์ตรวจคนเข้าออกทำงาน

การทดสอบ visitor-registration 29/29 เป็นผล Integration ก่อนหน้าบนฐานทดสอบ ไม่ใช่การทดสอบประตูจริง; ชุดหน้าจอและ logic ที่รวมใน frontend regression ล่าสุด 136/136 ไม่ใช่การคลิก Browser ทุกหน้า

**ตำแหน่งภาพ 4.12 (แบบฟอร์มลงทะเบียนผู้มาติดต่อ):** ใช้ข้อมูลและภาพเอกสารจำลอง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.12 แบบฟอร์มลงทะเบียนผู้มาติดต่อ
**ตำแหน่งภาพ 4.13 (หน้าสรุป/ดาวน์โหลดหลักฐาน PNG):** ต้องปิดชื่อ เบอร์ ที่อยู่ และข้อมูลบัตร
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.13 หน้าสรุป/ดาวน์โหลดหลักฐาน PNG
**ตำแหน่งภาพ 4.14 (หน้าผู้ดูแลแสดงลำดับการเข้าพบ):** แสดง WAITING/ADMITTED/COMPLETED พร้อมคำกำกับว่าเป็นการบันทึกโดยเจ้าหน้าที่ ไม่ใช่การเปิดประตูจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.14 หน้าผู้ดูแลแสดงลำดับการเข้าพบ

## 4.8 ผลการพัฒนาระบบ OCR

OCR ทำงานเป็น wrapper ส่งภาพเอกสารไปบริการภายนอกและรับผลอ่านข้อความกลับ ระบบบันทึกผล verification และผูกกับเจ้าของภาพ ผู้สมัครตรวจแก้ชื่อ วันเกิด เลขบัตรและที่อยู่ก่อนส่งต่อ Backend ตรวจเจ้าของ verification และความสัมพันธ์ของไฟล์ ไม่รับค่าที่กรอกจาก browser เพียงอย่างเดียวเป็นหลักฐานยืนยันตัวตน การอ่านเอกสารและการตรวจสลิปชำระเป็นคนละกระบวนการ; ผลอ่านข้อความจากสลิปไม่แทนผลธุรกรรมจากบริการชำระเงิน

ชุดทดสอบ unit/mock ตรวจ validation, ownership, การแสดงและแก้ข้อมูล, timeout/fallback ตามกรณี แต่ยังไม่มีชุดภาพบัตรที่ได้รับอนุญาตพร้อมคำตอบอ้างอิงรายฟิลด์ จึงยังคำนวณความแม่นยำ OCR เป็นเปอร์เซ็นต์ไม่ได้ การทดสอบด้วย Mock ไม่ยืนยันคุณภาพ OCR provider จริง

**ตำแหน่งภาพ 4.15 (OCR ก่อนอ่านและหลังเติมผล):** ใช้บัตรสังเคราะห์/เอกสารที่ได้รับอนุญาตเท่านั้น แสดงการตรวจแก้ข้อมูลโดยปกปิดเลขบัตรเต็ม
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.15 OCR ก่อนอ่านและหลังเติมผล
**ตำแหน่งภาพ 4.16 (สถานะ OCR เมื่อบริการไม่พร้อม):** ใช้ภาพทดสอบและแสดงข้อความลองใหม่ โดยไม่แสดง log หรือข้อมูลส่วนบุคคล
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.16 สถานะ OCR เมื่อบริการไม่พร้อม

## 4.9 ผลการพัฒนาระบบ Face Verification

ระบบมี flow ขอความยินยอม FACE_ENROLLMENT ก่อนเปิดกล้องหรือส่งภาพ การลงทะเบียนส่งภาพเป็นชุดและบันทึก completion marker เมื่อ Backend ตรวจสถานะผู้พัก ห้อง และจำนวนภาพครบ 5 ภาพแล้ว หากบริการมีปัญหาก่อนครบ ระบบแจ้ง enrollment ไม่สมบูรณ์และให้ retry ภาพที่บันทึกสำเร็จแล้วอาจคงอยู่เพื่อทำขั้นตอนที่เหลือต่อ

การตรวจใบหน้าใช้ Face API ที่ระบบเชื่อมต่อผ่าน wrapper; Monitor ใช้ BlazeFace ช่วยตรวจกรอบก่อนเลือกภาพส่ง ส่วนการค้นหาใบหน้าเทียบ embedding มีลักษณะ 1:N ตาม implementation และ Backend ตรวจ matched, user_id, similarity, threshold, เจ้าของบัญชีและสิทธิ์ก่อนบันทึกผล ค่า similarity เป็นคะแนนความคล้าย ไม่ใช่เปอร์เซ็นต์ความแม่นยำ

ผลทดลองที่ผู้ใช้รายงานจำนวน 4 ภาพ ได้ผลตรงตามที่คาด 3 ภาพ และตรวจไม่พบใบหน้า 1 ภาพ คิดเป็น 75% เฉพาะชุดทดลองนี้ ไม่ใช่ accuracy ทั่วไป ไม่มีหลักฐานว่าทดสอบ liveness การป้องกันภาพถ่าย/วิดีโอ กล้องจริง ประตู/Edge จริง หรือ Face provider จริงครบวงจร

**ตำแหน่งภาพ 4.17 (คำชี้แจงและยินยอม Face Enrollment):** ใช้บัญชีทดสอบ ไม่แสดงใบหน้าจริงโดยไม่มีสิทธิ์เผยแพร่
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.17 คำชี้แจงและยินยอม Face Enrollment
**ตำแหน่งภาพ 4.18 (หน้าลงทะเบียนและสถานะจำนวนภาพ):** ใช้ภาพสังเคราะห์หรือผู้ยินยอม พร้อมระบุว่า UI แสดงสถานะลงทะเบียน ไม่ใช่ผลรับรองโมเดล
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.18 หน้าลงทะเบียนและสถานะจำนวนภาพ
**ตำแหน่งภาพ 4.19 (หน้าประวัติการตรวจใบหน้า):** ปกปิดชื่อและภาพ ระบุว่าไม่ใช่หลักฐานประตูจริงเปิด
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.19 หน้าประวัติการตรวจใบหน้า

## 4.10 ผลการพัฒนาการแจ้งเตือนและ Realtime

ระบบมีรายการแจ้งเตือนตามบัญชี แยกข้อมูลส่วนตัวของผู้พักออกจากรายการสำหรับ Admin มีสถานะอ่าน/ยังไม่อ่านและค่ากำหนดความต้องการรับแจ้งเตือน Socket.IO ใช้ส่งเหตุการณ์เมื่อเชื่อมต่อได้ ส่วนหน้าจอใช้การดึงข้อมูลผ่าน API ตามจุดที่ออกแบบไว้เป็นช่องทางสำรอง การเชื่อมต่อ Socket ที่ล้มเหลวไม่ควรทำให้ข้อมูลหลักหาย เพราะงานและประวัติถูกบันทึกใน PostgreSQL ก่อนส่ง event

Regression ล่าสุดครอบคลุม logic และสิทธิ์ในชุดทดสอบ แต่ไม่มีหลักฐาน Browser Acceptance ที่ยืนยันการเชื่อมต่อ Realtime จาก production endpoint ปัจจุบัน จึงไม่สรุปว่า Socket.IO production ใช้งานได้เสมอ

**ตำแหน่งภาพ 4.20 (แถบแจ้งเตือนของผู้พักและ Admin):** จัดภาพสอง role เป็นภาพย่อย (ก) ผู้พัก และ (ข) Admin ในกรอบภาพเดียว แสดงตัวอย่างรายการที่ไม่มีข้อมูลจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.20 แถบแจ้งเตือน (ก) ผู้พัก และ (ข) Admin

## 4.11 ผลการพัฒนารายงานและการตรวจสอบย้อนหลัง

หน้ารายงานธุรกิจสรุปข้อมูลการดำเนินงานและการเงินจากรายการที่ระบบบันทึก โดยแยกยอดชำระและการคืนเงินจริงตามข้อมูลธุรกรรม Dashboard มีตัวชี้วัดและกราฟเพื่อช่วยติดตามภาพรวม ส่วน AccessLog และ audit records ใช้ตรวจเหตุการณ์และการทำรายการตามสิทธิ์ รายงานเป็นผลรวมจากฐานข้อมูล ไม่ใช่หลักฐานการโอนเงินของธนาคารหรือการเปิดประตูจริง

**ตำแหน่งภาพ 4.21 (Dashboard ผู้ดูแล):** ปกปิดชื่อ ยอดเงินจริง ข้อมูลผู้พักและช่วงเวลาที่ระบุตัวบุคคลได้
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.21 Dashboard ผู้ดูแล
**ตำแหน่งภาพ 4.22 (รายงานธุรกิจ/รายการคืนเงินจริง):** ใช้ข้อมูลทดสอบ หรือปิดรายละเอียดบัญชีและหลักฐานก่อนนำลงเล่ม
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.22 รายงานธุรกิจ/รายการคืนเงินจริง

## 4.12 ผลการพัฒนาการจัดเก็บข้อมูลและการติดตั้ง

ระบบใช้ PostgreSQL เป็นแหล่งข้อมูลหลักและ Prisma จัดการ schema/migration; Redis ใช้ cache, rate limit, lock และสถานะชั่วคราว ไม่แทนข้อมูลธุรกรรมถาวร ไฟล์เอกสารและหลักฐานจัดเก็บแยกจากแถวฐานข้อมูลโดยเก็บ path อ้างอิง การลบผู้พักจึงตรวจทั้งข้อมูลสัมพันธ์และงานล้างไฟล์ Docker Compose ใช้จัดบริการ Backend, PostgreSQL, Redis, PgBouncer และ Nginx ตาม configuration ที่กำหนด ส่วนบริการ AI เชื่อมผ่าน API และไม่สรุปว่าอยู่ใน Compose หรือเปิดใช้งานในทุก environment

การตรวจ runtime หลังการ deploy ที่บันทึกไว้ยืนยัน health endpoint ตอบ 200 ในช่วงตรวจเท่านั้น ไม่ใช่ uptime ระยะยาว ผล retention รายปีหรือ backup/restore ที่ยังไม่มีการทดลองยืนยันไม่ถูกรายงานว่าใช้งานจริงครบแล้ว

**ตำแหน่งภาพ 4.23 (หน้าตั้งค่าเงื่อนไขสัญญา):** แสดงเฉพาะหน้าจอและใช้ค่าทดสอบ ไม่ถ่าย `.env`, token, secret หรือข้อมูลผู้ให้เช่าจริง
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.23 หน้าตั้งค่าเงื่อนไขสัญญา
**ตำแหน่งภาพ 4.24 (สถานะ cleanup หลังลบข้อมูลทดสอบ):** ใช้เฉพาะรายการทดสอบที่ปกปิดตัวตน ไม่แสดง path จริงหรือข้อมูลภายในระบบ
**คำบรรยายใต้ภาพสำหรับใส่เล่ม:** ภาพที่ 4.24 สถานะ cleanup หลังลบข้อมูลทดสอบ

## 4.16 สมรรถนะและความปลอดภัย

การทดสอบโหลดแบบ bounded ในเครื่องวันที่ 13 ต.ค. 2569 ใช้การลงทะเบียนผู้มาติดต่อสังเคราะห์ 12 คำขอ พร้อมกัน 4 คำขอ บันทึกแถวและ log สำเร็จ 12/12 และวัด RPS/TPS ได้ประมาณ 77.67 ในช่วงทดลองสั้น ผลนี้ไม่รวม gateway หรือ provider จริง และไม่ใช่การรับรองขีดความสามารถ production หรือ SLA

ผลความปลอดภัยเป็นการตรวจเฉพาะ role/owner/input/session/idempotency/files ตามกรณี ไม่ใช่รายงาน penetration test ทั้งระบบ ไม่มีผลเปรียบเทียบ cache ก่อน/หลังหรือ long-running memory profiling ที่จะกล่าวว่าเร็วขึ้น/ไม่รั่วทุกกรณี

## 4.17 ภาพประกอบที่ต้องจัดเตรียมและข้อจำกัด

บรรทัดที่ขึ้นต้นด้วย `[ภาพที่ ...]` คือคำแนะนำว่าต้องจับภาพหน้าจอใดและจัดวางตรงไหน ให้แทรกภาพจริงแทนบรรทัดคำแนะนำ แล้วคงบรรทัด **คำบรรยายใต้ภาพ** ไว้ใต้ภาพตามตัวอย่างที่เตรียมไว้ ยังไม่มีไฟล์ภาพหน้าจอแนบในบทนี้ เพราะไม่มี session เข้าระบบที่ใช้ถ่ายได้ ภาพที่ควรเก็บให้ครบประกอบด้วย Login, Dashboard, สมัครและสัญญา, จัดการห้อง, บิล/ยอดส่วนเกิน, คำขอคืนเครดิต, แจ้งซ่อม, ผู้มาติดต่อ, OCR, Face consent/enrollment/history, Realtime, รายงานธุรกิจ, ตั้งค่าสัญญา และ cleanup

ก่อนถ่ายให้ใช้บัญชีและข้อมูลทดสอบ ปกปิดชื่อ อีเมล เบอร์โทร เลขบัตร ที่อยู่ ใบหน้า QR สลิป cookie, token, secret และหลักฐานโอนเงินจริง ภาพคำขอคืนเครดิตควรถ่ายหลัง deploy และทดสอบ Browser Acceptance แล้ว ส่วนภาพประตูต้องกำกับชัดเจนว่าเป็นการจำลอง/บันทึกโดยเจ้าหน้าที่ ไม่ใช่การเปิดประตูจริง

ข้อจำกัดที่ยังไม่ยืนยัน ได้แก่ การทำงานกับกล้องและประตู/Edge จริง SMS และ provider ภายนอกจริง การทดสอบ liveness การประเมินความแม่นยำ OCR ด้วยชุดข้อมูลคำตอบอ้างอิง การประเมินความแม่นยำ Face จากกลุ่มตัวอย่างที่เพียงพอ การทดสอบความพึงพอใจผู้ใช้แบบมีตัวอย่าง และการทดสอบ backup/restore หรือ retention รายปีใน production การนำเสนอผลต้องแยกสิ่งที่ทดสอบผ่านออกจากสิ่งที่ยังอยู่นอกขอบเขต

## 4.18 ผลเพิ่มคำชี้แจงและความยินยอม — 14 ต.ค. 2569
