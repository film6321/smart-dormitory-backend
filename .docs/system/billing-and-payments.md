# 4.5 การพัฒนาระบบบิลและการชำระเงิน

## 1. แยกความหมายของข้อมูลการเงิน

| ข้อมูล | หน้าที่ |
|---|---|
| Bill | ยอดเรียกเก็บรายผู้พักและสถานะหนี้ |
| Payment | ความพยายาม/ผลชำระรายบิลหรือมัดจำสมัคร |
| PaymentBatch/Item | รวมบิลที่เลือกในธุรกรรมเดียวและรายการย่อย |
| HousingApplicationDraft | ฉบับร่างที่ผูกเครดิตสมัครกับบัญชี |

มัดจำสมัครและบิลรายเดือนไม่ใช่รายการเดียวกัน QR ที่สร้างได้ไม่ใช่หลักฐานว่าเงินเข้า และการอ่านสลิปสำเร็จไม่ใช่การอนุมัติผู้พัก มัดจำเข้าสรุปรายรับเมื่อเป็น PAID และมี housingApprovedAt จาก Admin

## 2. การสร้างบิลรายเดือน

Admin เลือกห้อง/รอบบิล ตรวจสมาชิกที่ยัง active และมีสิทธิ์ จากนั้นคำนวณค่าเช่า ค่าไฟ ค่าน้ำ และส่วนแบ่งรายคน ข้อมูลยอดเก็บแยกประเภทใน Bill ไม่ให้หน้าเว็บแยกเงินเองจากประโยค description

รอบเก็บเป็น YYYY-MM การออกบิลซ้ำห้อง/ผู้พัก/รอบมี guard และ unique constraint การแบ่งสตางค์กระจายเศษตามลำดับที่ service กำหนดให้ผลรวมเท่ากับยอดทั้งห้อง จำนวนคนหารเป็นข้อมูล ณ วันออกบิล ไม่เปลี่ยนย้อนหลังตามสมาชิกใหม่

## 3. Flow ชำระบิล

1. User อ่านเฉพาะบิลของตนเอง เลือกบิล UNPAID/OVERDUE และดูยอดรวม
2. สร้าง PaymentBatch ด้วย idempotency key และขอ QR จาก wrapper
3. โอนเงินภายนอกและแนบสลิป ระบบตรวจ transaction, จำนวนเงิน และหลักฐานตาม policy
4. ระหว่าง VERIFYING ไม่ส่งซ้ำ; ผลสำเร็จเป็น PAID ส่วน FAILED/MANUAL_REVIEW ต้องแสดงเหตุผลหรือรอตรวจ
5. รีเฟรชอ่านสถานะจาก server ไม่อ้างความสำเร็จจากหน้าผลลัพธ์อย่างเดียว

สถานะ Bill มีเส้นทาง UNPAID/OVERDUE → VERIFYING → PAID หรือ FAILED การกลับจาก FAILED ใช้กฎของ service ไม่อนุญาตการแก้ข้ามสถานะโดยไม่มีสิทธิ์

## 4. มัดจำสมัครและเปลี่ยนห้อง

ยอดที่ชำระผูกบัญชี/draft ฝั่ง server เมื่อรีเฟรชต้องตรวจเครดิตก่อนให้จ่ายซ้ำ เปลี่ยนเป็นห้องแพงกว่าคำนวณเฉพาะส่วนขาดจากยอดที่ตรวจผ่าน ห้องถูกกว่าต้องแสดง excess ตามข้อมูล server ไม่เรียกสิ่งนี้ว่าระบบคืนเงินอัตโนมัติ

server ตรวจราคาห้องและสัญญาส่วนกลางก่อนสร้าง QR การบันทึก draft 200 ไม่ได้แปลว่าชำระได้หากเงื่อนไข Admin ยังไม่ครบ หรือข้อมูลเบอร์บัญชีหาย

## 5. UI และรายละเอียดบิล

หน้ารายละเอียด Admin ใช้ modal เดียว มีเลขบิล สถานะภาษาไทย ยอด ผู้พัก ห้อง กำหนดชำระ ตารางประเภทค่าใช้จ่าย ประวัติชำระและสลิป ภาพใช้ contain ไม่บิดเบี้ยว

ตารางค่าใช้จ่ายใช้ rentAmount/electricAmount/waterAmount/penaltyAmount และตรวจว่าผลรวมตรง amount ถ้าข้อมูลเก่าแยกประเภทไม่ได้ให้แสดงยอดรวมพร้อมข้อความอธิบาย ไม่สร้างยอดสมมติ หน้าผู้พักแบ่งหน้าละ 5 บิลค้าง และซ่อนแถบเปลี่ยนหน้าเมื่อมี 0–5 บิล

## 7. ผลทดสอบ

| กรณี | ผล/หลักฐาน |
|---|---|
| เครดิตหลัง remount/เปลี่ยนห้อง/เติมยอด | IT ด้วย mock provider ตามชุด housing-payment |
| สลิป/transaction เดิม | UT/IT ตรวจ idempotency และปฏิเสธซ้ำตามกรณี |
| ออกบิลซ้ำ/แบ่งสตางค์ | IT ตาม QA |
| ชำระบิล #58 | ผู้ใช้ชำระเอง; RT อ่าน PAID 100 บาท |
| ย้ายออกขณะยัง UNPAID | RT 409 ไม่ข้าม guard |
| QR เก่า PENDING แต่ไม่มีหลักฐาน ทุกบิล PAID | IT และ RT purge ลบพร้อมผู้พัก |
| PENDING ที่มีหลักฐาน หรือ VERIFYING | IT DELETE 409 |
| ธนาคาร/provider settlement จริง | OS; ผลผู้ใช้รายงานไม่ใช่การรับรอง provider |

## 8. กันที่พักก่อนชำระเงิน — 18 ตุลาคม 2569

ก่อนสร้าง QR มัดจำ ระบบล็อก User และ Room แล้วตรวจจำนวนผู้พัก/ใบสมัครที่จองอยู่ รวมกับสิทธิ์ชั่วคราวของผู้สมัครคนอื่น หากเหลือหนึ่งที่ มีเพียงคนเดียวได้สิทธิ์และเรียกสร้าง QR ผู้ที่ไม่ได้สิทธิ์ได้รับ 409 ก่อนส่งไปจ่ายเงิน สิทธิ์เก็บใน HousingApplicationDraft.roomHoldExpiresAt ของ PostgreSQL ไม่ใช้ Redis เป็นข้อมูลหลัก

สิทธิ์เริ่มต้น 10 นาที การกดขอ QR ซ้ำไม่ต่อเวลาเดิม เมื่อครบกำหนด PostgreSQL จะไม่นับ hold นั้นเป็นที่พักที่ถูกจองอีกต่อไป โดยไม่ต้องรอ worker และจะล้างวันหมดอายุเมื่อเจ้าของโหลด draft ครั้งถัดไป ยอด PAID ยังคงเป็นเครดิตของเจ้าของ draft ส่วนรายการ VERIFYING, PENDING, MANUAL_REVIEW หรือธนาคารรอยืนยันยังเก็บสถานะเพื่อตรวจสอบ แต่ไม่ยืดสิทธิ์ห้อง หากจ่ายหรือส่งหลักฐานหลังหมดเวลา ระบบเก็บผลตรวจเป็นเครดิตและไม่แย่งห้องที่มีผู้ได้สิทธิ์ไปแล้ว

การยื่นใบสมัครเปลี่ยนจาก hold เป็น Tenant PENDING ภายใน transaction เดียวกัน ไม่คิดจำนวนซ้ำ Admin เพิ่มหรือย้ายผู้พักต้องตรวจ holds ด้วย และไม่ลบ/ปิด/เปลี่ยนเลขห้องหรือลดจำนวนต่ำกว่าที่ใช้ขณะมีสิทธิ์อยู่ เมื่อเปลี่ยนห้องใน draft จะคืน hold เดิม แล้วต้องขอ QR ของห้องใหม่เพื่อกันที่อีกครั้ง

หากโอนหลังหมดสิทธิ์แล้วห้องเต็ม ระบบยังตรวจและเก็บยอดที่ผ่านเป็นเครดิตของเจ้าของ แต่ไม่ยึดที่จากผู้ถือสิทธิ์คนใหม่ การยื่นสมัครต้องตรวจความจุซ้ำ ยอดเดิมใช้เลือกห้องอื่นได้ตามเงื่อนไข หรือให้ผู้ดูแลจัดการเรื่องเงิน การหมดเวลาบนเว็บไม่ได้ยกเลิก PromptPay QR ในแอปธนาคาร และยังไม่มีการคืนเงินอัตโนมัติ

หลักฐาน: [integration ทดสอบห้องที่เหลือที่เดียว](../../tests/integration/housing-room-hold.test.ts) 8/8 ผ่านกับ PostgreSQL แยกและ provider จำลอง รวม QR พร้อมกัน, Admin แข่งกับ QR, หมดอายุ, ตรวจเงินค้าง, เปลี่ยนห้อง และสองคนมีเงินโอนแต่ยืนยันห้องได้เฉพาะผู้ถือสิทธิ์ ไม่ใช่ผลโหลด RPS/TPS หรือการโอนเงินจริงผ่านธนาคาร

## 9. การลบและข้อจำกัด

เมื่อ guarded purge ผ่าน บิล/การชำระที่ผูกผู้พักถูกลบและไม่อยู่ในยอด Dashboard ต่อ ไม่มีการเก็บยอดนิรนามแทน การลบข้อมูลไม่ใช่การคืนเงินผ่านธนาคาร รายการร่วมกับคนอื่นหรืออยู่ระหว่างตรวจต้องจัดการก่อนลบ

รูปที่ควรใช้: หน้าเลือกบิล QR ที่ปิดข้อมูลผู้รับ ตารางแจกแจง สถานะ PAID และผลรีเฟรช ห้ามแนบสลิปจริงเต็มภาพในเล่ม

## เงื่อนไขความยินยอมสำหรับการสมัคร (14 ต.ค. 2569)

API สร้าง QR มัดจำและอัปโหลดสลิปของใบสมัครต้องมี HOUSING consent ของบัญชีปัจจุบันเพิ่มเติมจาก guard เดิม ไม่ใช้เป็นการยืนยันยอดเงินหรือแทนการยอมรับสัญญา หากต้องอ่านคำชี้แจงใหม่ เครดิต/ยอดที่จ่ายแล้วในฉบับร่างยังคงอยู่ ไม่สร้างรายการจ่ายซ้ำ การชำระบิลของผู้พักเดิมไม่ได้เพิ่ม checkbox ใบหน้า ดู [ผู้พักและสัญญา](users-and-tenants.md)


## คำขอคืนเครดิตจากใบสมัคร (19 ต.ค. 2569)

เครดิตที่จ่ายแล้วคงอยู่หลังหมดเวลากันห้อง ผู้สมัครเลือกเก็บไว้ใช้สมัครต่อ หรือส่งคำขอคืนเครดิตทั้งหมดจากหน้าสมัครได้ เมื่อมีคำขอ ระบบปล่อยสิทธิ์ห้องและพักการแก้ใบสมัคร/อัปโหลด/ชำระ/ยื่นไว้ระหว่างรอ Admin เพื่อไม่ให้ใช้เครดิตก้อนเดียวกันซ้ำ

Admin จัดการคำขอในกล่อง “คำขอคืนเงินจากใบสมัคร” ภายในหน้า **จัดการผู้พักอาศัย** ซึ่งอ่านจาก HousingApplicationDraft จึงเห็นผู้สมัครได้แม้ยังไม่มี Tenant หรือเอกสาร ผู้ดูแลปฏิเสธพร้อมเหตุผลได้โดยเครดิตยังอยู่ หรือบันทึกการคืนเงินจริงหลังโอนภายนอกแล้ว พร้อมยอด เลขอ้างอิง หลักฐาน และการยืนยัน ระบบไม่โอนเงินเองและไม่ลบ Payment เดิม เมื่อคืนเงินจริงแล้วจึงหักยอดจากเครดิต; รายงานธุรกิจแสดงผลทางการเงินที่บันทึกแล้ว

HousingRefundRequest บันทึกสถานะ PENDING/COMPLETED/REJECTED แยกจาก HousingRefund ซึ่งเก็บรายการคืนเงินจริง หลักฐานเป็น private และลบพร้อมข้อมูลที่ผูกบัญชีตาม guarded purge. API: POST /api/tenants/draft/refund-request (ผู้สมัคร), GET /api/tenants/drafts/refunds (Admin), POST /api/tenants/drafts/:draftId/refund-requests/:requestId/reject (Admin), POST /api/tenants/drafts/:draftId/refunds และ GET /api/tenants/drafts/refunds/:refundId/proof (Admin).
