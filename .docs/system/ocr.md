# 4.9 การพัฒนาส่วนอ่านเอกสาร OCR

## 1. หน้าที่

OCR wrapper รับภาพเอกสาร ส่งบริการภายนอก และแปลงผลให้โมดูลสมัคร/ผู้มาติดต่อใช้งาน ไม่ติดตั้ง engine อ่านเอกสารขึ้นในระบบหอพักเอง ผลอ่านต้องให้ผู้ใช้ตรวจแก้และตรวจความสัมพันธ์อีกครั้งที่ server

การอ่านบัตรกับการตรวจสลิปเป็นคนละความหมาย การชำระต้องใช้ผลธุรกรรมของ payment wrapper ไม่ใช่แค่เห็นจำนวนเงินในภาพ

## 2. Flow และ UX/UI

1. ผู้ใช้วางหรือเลือกภาพ ระบบตรวจประเภท/ขนาดตาม route
2. แสดงภาพตัวอย่างให้พอดีพื้นที่และวางกลาง โหลดอยู่ภายในช่องภาพ
3. ส่งอ่านอัตโนมัติเมื่อเลือกไฟล์ ป้องกันการตรวจซ้อน/response เก่าทับภาพใหม่
4. คืน verificationId และข้อมูลอ่านได้ เติมชื่อ/นามสกุล วันเกิด เลขบัตร และที่อยู่
5. แยกคำนำหน้าก่อนแบ่งชื่อ ป้องกัน “นาย” ถูกใส่เป็นชื่อและชื่อจริงไปอยู่ในนามสกุล
6. ผู้ใช้ตรวจแก้ข้อมูลพร้อมข้อความสั้นใต้ภาพ ก่อนเดินไปขั้นถัดไป

วันเกิดใช้ date input ไม่แสดงข้อความวันเกิดจาก OCR สีแดงซ้ำใต้ช่องเป็นข้อความถาวร หากอ่านไม่ผ่านให้แสดง error และปุ่มลองใหม่ขนาดเหมาะสม ไม่ล้างข้อมูลที่ผู้ใช้กรอกเองโดยไม่มีเหตุ

## 3. ข้อมูลและการยืนยันเจ้าของ

IdCardVerification เก็บผลตรวจและ path ของภาพ OcrJob เก็บงานอ่านและสถานะที่ต้องกู้ผลได้ ระบบตรวจ verification, ภาพ และเจ้าของเมื่อใช้ผลในใบสมัคร/Visitor ข้อมูลส่วนตัวที่ client ส่งไม่แทนการมีหลักฐาน OCR ที่ถูกต้อง

User.phone เป็นข้อมูลบัญชี ไม่ใช่สิ่งที่ OCR บัตรต้องอ่าน การไม่มีเบอร์บัญชีอาจขวางส่งใบสมัคร จึงต้องแสดงความผิดพลาดตรงหน้าที่เหมาะสม ไม่กล่าวว่าสลิปหรือบัตรเสียจากสาเหตุนี้

## 4. API ตัวอย่างและข้อจำกัด upload

| Endpoint | หน้าที่ |
|---|---|
| POST `/api/ocr/verify-id-card` | OCR บัตร; มี alias ตาม routes |
| POST `/api/ocr/verify-id-card/jobs` | สร้าง job |
| GET `/api/ocr/verify-id-card/jobs/:jobId` | อ่านผล job ตามกฎใน controller |
| POST `/api/tenants/draft/upload-identity` | ใช้ผลกับ draft บัญชี |
| POST `/api/visitor/scan-id-card` | ใช้ flow ผู้มาติดต่อ |

ขนาดและ field name ต่างกันระหว่าง OCR, tenant และ visitor routes ตัวอย่าง route OCR จำกัด 5MB และรับ MIME JPEG/PNG/WebP ไม่ควรคัดลอกข้อความ “10MB” ของหน้าอื่นไปอธิบายทุก endpoint ต้องตรวจ wrapper และ route ที่ใช้งานจริง

## 5. Timeout, fallback และข้อมูลตกค้าง

wrapper กำหนด timeout และรักษา fallback ที่มีอยู่ ภายนอกขัดข้องไม่ควรสร้างสถานะยืนยันสำเร็จโดยเดาข้อมูล job/error ต้องอ่านได้ตาม API ไฟล์ที่ไม่ใช้มีวงจร cleanup และตอน purge ต้องล้างภาพ/jobs/verifications ของเจ้าของด้วย

รายการ OCR บางส่วนใช้ Redis cache เป็นสำเนาเพื่ออ่านเร็ว เมื่อเปลี่ยนหรือลบต้อง invalidate ไม่ยก Redis เป็นแหล่งเก็บผลหลัก ระยะเวลาหรือประสิทธิภาพจริงต้องอิงผลวัด ไม่อนุมานจากการมี cache

## 6. ผลทดสอบ

| กรณี | ผล/หลักฐาน |
|---|---|
| Payload/ไฟล์ไม่ถูกต้อง | UT/IT ปฏิเสธตามข้อกำหนด |
| ใช้ verification/ภาพคนอื่น | IT ตรวจ ownership |
| จัดชื่อคำนำหน้าและวันเกิด | UT frontend และ source review |
| ยืนยันใบสมัครข้ามข้อมูลจำเป็น | UT/IT ปฏิเสธ |
| ภายนอก timeout/fallback | UT/mock ไม่ใช่ provider จริง |
| OCR ผ่านหน้าเว็บ | ผู้ใช้รายงานปกติ; UA |
| purge ข้อมูลบัตรและภาพเจ้าของ | RT ข้อมูล 0 และไฟล์หายตาม snapshot |
| Accuracy OCR ทุกแบบบัตร | OS/ไม่มีชุดข้อมูลประเมิน |
