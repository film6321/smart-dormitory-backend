# 4.4 การพัฒนาระบบจัดการห้องพัก

## 1. หน้าที่และสิทธิ์

Room เก็บเลขห้อง ชั้น ความจุ ราคา สถานะ และรายละเอียด Admin สร้าง/แก้ไข/ลบ ส่วน STUDENT อ่านรายการเพื่อสมัครเข้าพักได้ การอ่านห้องต้องไม่เท่ากับการอ่านเอกสารส่วนตัวของผู้พักร่วม

## 2. หน้าจอ

หน้าห้อง Admin แสดงการ์ดเลขห้อง สถานะ จำนวนคน/ความจุและที่ว่าง ช่องค้นหาค้นเลขห้องหรือข้อมูลที่รายการมีสิทธิ์แสดง พร้อมกรองชั้น รายละเอียดห้องแสดงข้อมูลหลัก ผู้พัก และงานซ่อมที่เกี่ยวข้อง

Service ใช้ AVAILABLE/OCCUPIED ในการคำนวณห้องที่รับผู้พักได้ ส่วนกลุ่ม “ว่าง/รับเพิ่ม/เต็ม/ไม่พร้อมใช้” บนหน้าจอต้องตีความร่วมกับจำนวนคนและความจุ ไม่ถือว่าเป็น enum ฐานข้อมูลชื่อเดียวกันทั้งหมด การ์ดเต็มไม่ควรใช้สีผิดพลาดหากเป็นสถานะปกติของธุรกิจ การแสดงอาคาร A เป็นค่า UI ที่เจ้าของโครงการกำหนดสำหรับระบบปัจจุบัน ไม่ใช่หลักฐานว่าฐานข้อมูลมี Building model แยก

## 3. Flow และกฎความจุ

1. Admin เพิ่มห้อง ระบบตรวจข้อมูลและเลขห้องซ้ำ
2. User อ่านห้องที่เลือกได้และบันทึกความต้องการใน draft
3. การส่งใบสมัคร/อนุมัติต้องตรวจความจุจริงใน transaction ไม่เชื่อจำนวนว่างจากหน้าเว็บ
4. Tenant PENDING ที่ active ถูกนับเป็นการจองสิทธิ์ตาม filter ของระบบ
5. เมื่อย้ายออกหรือปฏิเสธ ห้องถูกคืนและคำนวณสถานะใหม่
6. การลบห้องต้องผ่านกฎความสัมพันธ์ ไม่ลบห้องที่ยังมีข้อมูลเกี่ยวข้องเพื่อข้ามข้อจำกัด

ความจุที่ใช้พิจารณาเป็นค่าห้องร่วมกับเพดานการพักจาก settings ตาม service เมื่อมีผู้สมัครพร้อมกันต้องตรวจหลังล็อกอีกครั้ง ป้องกันหน้าเว็บทั้งสองเห็นที่ว่างเดียวกันแล้วอนุมัติเกินจำนวน

## 4. ราคาและข้อมูลสัญญา

ราคาห้องเป็นฐานสำหรับเงื่อนไขสมัครและการชำระ หาก Admin เปลี่ยนราคาในขณะที่มี Tenant, draft OPEN หรือรายการชำระที่เกี่ยวข้อง ระบบปฏิเสธ 409 ตาม guard ไม่เปลี่ยนราคาสัญญาและยอดที่ผู้ใช้กำลังชำระเงียบ ๆ สัญญาที่ส่งแล้วเป็น snapshot

## 5. API และข้อมูล

| Method / endpoint | สิทธิ์ |
|---|---|
| GET `/api/rooms` | ADMIN/STUDENT |
| GET `/api/rooms/:id` | ADMIN/STUDENT |
| POST `/api/rooms` | ADMIN |
| PATCH `/api/rooms/:id` | ADMIN |
| DELETE `/api/rooms/:id` | ADMIN |

ข้อมูลสัมพันธ์หลักคือ Tenant.roomId, draft.roomId, payment.housingRoomId และบิลห้องตามรอบ การรวมค่าห้องในรายงานต้องอิงข้อมูลเหล่านี้ ไม่อนุมานประวัติจากจำนวนผู้พักปัจจุบัน

## 6. ผลทดสอบ

| กรณี | ผลที่ตรวจ | ประเภท |
|---|---|---|
| ไม่มี session อ่านรายการ | ปฏิเสธ | RT/IT |
| User แก้ห้อง | ปฏิเสธสิทธิ์ | IT |
| แย่งที่ว่าง/ตรวจ reservation | transaction ตรวจจำนวนปัจจุบัน | IT ในชุด housing/maintenance ตาม QA |
| เปลี่ยนราคาเมื่อมีรายการผูก | 409 | IT |
| ย้ายออกผู้พักทดสอบ | roomId ของ Tenant null | RT |
| หลัง purge ผู้พักสุดท้าย | ห้อง id 159 AVAILABLE, Tenant ในห้อง 0 | RT |

ผลคืนห้องจากกรณีหนึ่งไม่ใช่หลักฐานว่าทดสอบทุกรูปแบบของ capacity และทุกสถานะห้องด้วย browser แล้ว
