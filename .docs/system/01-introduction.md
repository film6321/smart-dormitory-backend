# บทที่ 1 บทนำ

> เอกสารอิงระบบ MEEDEE Dormitory ณ 13 ต.ค. 2569 ต้องเติมชื่อผู้จัดทำ สถานศึกษา และรูปแบบอ้างอิงตามข้อกำหนดของหลักสูตรก่อนจัดเล่ม

## 1.1 ที่มาและปัญหา

งานหอพักมีข้อมูลที่สัมพันธ์กัน ได้แก่ บัญชีผู้ใช้ ใบสมัครเข้าพัก ห้อง สัญญา บิล งานแจ้งซ่อม และผู้มาติดต่อ หากแต่ละหน้าจัดการสถานะต่างกัน ผู้ดูแลอาจเห็นข้อมูลคลาดเคลื่อน เช่น งานที่อนุมัติแล้วหายจากรายการ หรือผู้พักที่ย้ายออกยังผูกกับห้อง ระบบนี้รวมงานเหล่านี้ผ่านฐานข้อมูลกลางและแบ่งโมดูลตามหน้าที่

ปัญหาที่พบระหว่างพัฒนาประกอบด้วย UI ไม่เป็นมาตรฐาน เอกสารไม่ตรงโค้ด สถานะการแจ้งซ่อมที่แก้ต่อได้หลังจบงาน และความต่างระหว่างไฟล์ล่าสุดกับ Docker image ที่รันจริง ประเด็นเหล่านี้เป็นเหตุผลในการจัดกฎ UI ตรวจ API และบันทึกหลักฐานการทดสอบ

## 1.2 วัตถุประสงค์

1. จัดการวงจรผู้พักตั้งแต่สมัคร ตรวจเอกสาร เข้าพัก จนถึงย้ายออก
2. เชื่อมข้อมูลห้อง บิล งานซ่อม และผู้มาติดต่อ โดยกำหนดสิทธิ์และสถานะที่ตรวจสอบได้
3. ใช้ OCR และ Face Verification ผ่านบริการภายนอก ไม่สร้าง engine ประมวลผลขึ้นใหม่เอง
4. ทำ UX/UI และสถานะ Loading/Empty/Error ให้สอดคล้องกันและรองรับขนาดหน้าจอ
5. ทดสอบพฤติกรรมที่สำคัญและจัดเอกสารส่งมอบให้ตรวจสอบกับโค้ดได้

## 1.3 ขอบเขต

| กลุ่ม | งานในขอบเขต |
| --- | --- |
| Student | บัญชี สมัครเข้าพัก ดูข้อมูลตนเอง บิล แจ้งซ่อมตามสิทธิ์ |
| Admin | ห้อง ผู้พัก สถานะใบสมัคร งานซ่อม บิล ผู้มาติดต่อ ตั้งค่า และข้อมูลภาพรวม |
| ผู้มาติดต่อ | อ่านบัตร กรอกข้อมูลและห้องที่ติดต่อ ยินยอม และส่งคำขอ |
| การเชื่อมต่อภายนอก | wrapper และการจัดการผล/ข้อผิดพลาดด้วย mock; ไม่รับรอง provider จริง |

Face Verification เป็นฟีเจอร์ที่เก็บไว้และแก้บั๊กเท่านั้นตามขอบเขตที่ผู้ใช้กำหนด ไม่เพิ่ม engine หรืออ้างความแม่นยำจากคะแนนหน้าจอ การตรวจธุรกรรมเงินจริงในรอบนี้ผู้ใช้เป็นผู้ทดสอบเอง

## 1.4 วิธีดำเนินงาน

ตรวจสัญญาและโค้ด → แก้ตรรกะ → ปรับ UI → ตรวจ Loading/Empty/Error → ทดสอบอัตโนมัติและ API จริง → บันทึกผล → จัดเอกสาร คำแนะนำขณะพิมพ์ค้นหาและการเลือกคณะจากรายการ Admin เป็นส่วนที่ปรับในระบบปัจจุบัน

## 1.5 ประโยชน์ที่คาดหวังและข้อจำกัด

ลดการกรอกข้อมูลซ้ำและทำให้สถานะมีความหมายเดียวกันทั้งระบบ ช่วยให้ผู้พัฒนารับช่วงดูแลระบบตามโมดูลได้ แต่ประโยชน์เชิงตัวเลข เช่น ลดเวลาทำงานกี่เปอร์เซ็นต์ ต้องมีการวัดจริงก่อนกล่าวอ้าง

ผลทดสอบ local ไม่ยืนยัน production ทั้งหมด และยังไม่มีการศึกษาความพึงพอใจหรือทดลองกับผู้ใช้จำนวนมากในเอกสารนี้

## 1.6 ขอบเขตการส่งมอบปัจจุบัน

เว็บ Admin/User/Visitor, HTTP authorization/validation, PostgreSQL, ไฟล์, draft/credit, idempotency และ cleanup อยู่ในขอบเขต กล้อง/ประตู/Edge จริง SMS จริง และ provider ภายนอกจริงเป็น Out of scope ของรอบ QA รายละเอียดบทที่ 4 แยกเป็นเอกสารโมดูลใน [สารบัญระบบ](README.md) เพื่อให้ติดตามจากหน้าจอไปถึงข้อมูลและผลทดสอบได้

บัญชี User แยกจาก Tenant สมัครเข้าพัก 4 ขั้น และ guarded purge ลบข้อมูลผูกผู้พักทั้งหมดพร้อมเก็บ User ไม่ใช้ ARCHIVED หรือบิลนิรนามแทนการลบตามนโยบายปัจจุบัน
