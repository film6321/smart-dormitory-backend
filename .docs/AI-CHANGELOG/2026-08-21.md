## สิ่งที่ทำเสร็จ

- [face-verification] เชื่อม flow การบันทึกภาพใบหน้ากับ `FaceEnrollmentPhoto` และจัดเก็บไฟล์ไว้ที่ `uploads/face-photo` เพื่อรองรับการนำไปประมวลผลต่อโดย FaceGate.Edge
- [access-control] ใช้ `MonitorPage` เป็นฐานของหน้า `/access-control` เพื่อรวมกล้อง, recognition result, scan history, device status และ activity log ไว้ใน flow เดียว
- [door-control] เพิ่ม `POST /api/face-verification/door-command` สำหรับคำสั่ง `lock` และ `unlock` โดยตรวจสอบ JWT และสิทธิ์ `ADMIN` พร้อมคืนค่า standardized API response
- [frontend] เชื่อมปุ่ม Unlock/Lock ในหน้า monitor เข้ากับ backend จริง เพิ่มการแสดงผลสำเร็จและการคืนสถานะเมื่อคำสั่งล้มเหลว
- [testing] เพิ่ม integration test สำหรับคำสั่งเปิดและล็อกประตู และตรวจสอบ backend test suite ผ่าน 32 tests รวมถึง frontend production build ผ่าน

## ปัญหาที่แก้ไข

- แก้การเรียก endpoint จาก frontend ที่เดิมชี้ไปยัง `/access-control/door-command` ให้ใช้ `/face-verification/door-command` ซึ่งตรงกับ route จริง
- เพิ่ม validation สำหรับ `device_code` และ `action` เพื่อป้องกันคำสั่งประตูที่ไม่สมบูรณ์หรืออยู่นอกเหนือจาก `lock`/`unlock`
- เพิ่ม error handling ฝั่ง monitor ไม่ให้ UI ค้างสถานะ UNLOCKED เมื่อ backend ไม่สามารถรับคำสั่งได้

## สิ่งที่ยังค้างอยู่

- การตรวจจับและเปรียบเทียบใบหน้าใน local environment ยังใช้ fallback mock เมื่อไม่ได้ตั้งค่า `FACE_API_URL` และ `FACE_API_KEY`; ต้องเชื่อม Face API หรือ FaceGate.Edge เพื่อทดสอบ biometric matching จริง
- `door-command` ในปัจจุบันเป็น API command/status layer และยังไม่ได้เชื่อมอุปกรณ์ประตูจริงหรือบันทึกคำสั่งลงตาราง audit เฉพาะ
- ควรเพิ่ม QA/Postman flow สำหรับ register -> ตรวจสอบข้อมูลในฐานข้อมูล -> capture จาก monitor -> verify -> ตรวจผล recognition และ door decision
